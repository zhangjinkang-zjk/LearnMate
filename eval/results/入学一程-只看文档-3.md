## 一、诊断问答

### 第 1 问（难度 easy）

**导师问**：在你看来，一个智能体为什么要设计"工具调用"这个能力？比如它和直接把所有知识都塞进模型里，差别在哪？

**假学生答**：我觉得核心是模型的参数容量和知识都是"死"的，训练完就固定了，但工具能接的是活的数据——比如实时查天气、查数据库，这个没法全塞进模型里，而且直接塞进去上下文窗口也撑不住，文档里也常说这叫"给模型开一扇通往外部世界的门"。另外工具调用让模型只在需要的时候才去拿特定信息，而不是把所有可能用到的东西都堆在 prompt 里，这样既省 token 又更可控。不过说实话我只看过文档和视频里这样讲，还没自己写过一个真正跑通的 function calling 流程，所以具体实现上会不会有坑我还答不上来。

**判分**：答错（0.0）

**给学生的反馈**：你讲清了工具调用解决数据时效和上下文限制的道理，但没说模型怎么依据工具描述判断该不该调用，这一环还没吃透。

### 第 2 问（难度 easy）

**导师问**：你说还没真跑通过一次流程，那按你看文档的印象，用户问“北京今天天气怎么样”之后，模型和你写的程序之间要来回几次、每次各干什么？

**假学生答**：按我看文档的印象大概是两轮：第一轮是模型收到问题后不直接回答，而是在响应里吐一个结构化的调用请求，比如带工具名"get_weather"和参数{"city": "北京"}，我的程序解析出来后真正去调那个函数、拿到天气数据；第二轮是把工具返回的结果作为一条新的消息塞回对话里再发给模型，模型才组织成自然语言回答用户。我记得文档里把第一次那个"要调工具"的响应叫 tool call、把结果那条消息叫 tool result，但具体程序里怎么把它们串起来、错误了怎么处理，我还没自己动手写过，就只是看教程里这么跑了一遍。

**判分**：答错（0.0）

**给学生的反馈**：结构化调用、由程序执行并把结果回填这三步你说对了，但没提到请求时要先把工具定义一并发给模型，缺了这一步模型并不知道工具的存在。

### 第 3 问（难度 easy）

**导师问**：模型凭什么知道该调你写的哪个工具、参数该填什么？比如你给它登记的那段工具说明，起的到底是什么作用？

**假学生答**：我看文档的理解是，那段工具说明（就是函数名、描述、参数 schema 那套 JSON）会作为可选工具列表发给模型，模型是靠描述里的自然语言去判断该不该调、调哪个——比如描述里写"查询某城市当前天气"，用户问天气它就匹配上了，参数该填什么也是靠你给的参数字段的 name 和 description 提示它从用户话里抽哪些值填进去。所以这段说明其实就相当于你在用自然语言给模型写"接口文档"，写得含糊它就容易填错参数或者根本不调。但这些都是我看文档和教程里的说法，比如 OpenAI function calling 那篇，我还没自己试过描述写得烂一点会坏成什么样，所以到底多敏感我也说不准。

**判分**：答对（100.0）

**给学生的反馈**：你把工具信息会发给模型、靠描述匹配意图来选工具和抽参都说清楚了，还意识到描述含糊的后果，欠缺的只是没亲自验证过敏感度。

- 知识点：工具注册、工具描述、参数 schema

</details>
