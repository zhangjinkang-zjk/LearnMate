### 第 1 轮

**学生**：我想做一个多智能体的资料问答程序，用 LangGraph，感觉比较火。

**工具调用**：（一个都没有）

**教练**：

你选 LangGraph 这一步本身站得住 —— 不是因为它火，而是因为这次要练的核心正是「状态在多个 agent 之间怎么传」，状态图就是干这个的。但**「因为火」不是理由**，方案里「为什么用它」那一栏你迟早要换成一句真话：它解决了你这个程序里的哪个具体问题（比如 A agent 查完的结果怎么交给 B agent、中途错了怎么原路返回）。

真正的缺口在前半句：**「多智能体的资料问答程序」还不是一个能动手的东西**。你有了技术栈，但没有问题——哪个专业领域、哪几份资料、给谁用、什么问题不答，一个都没有。而你要交的方案，第一段恰恰就是这些。多智能体怎么分工也不是拍脑袋定的，它取决于**答案散在哪几份资料里**：资料是两份互不相关的文档，还是一个大库加一份规范，拆出来的 agent 完全不同。

所以先问你一个问题，其他都从它长出来：

**你手边真实存在的那几份资料是什么？** 具体到——文件名或主题、格式（PDF / markdown / 网页 / 数据库）、大概多大。别报一个理想中的「整个领域的文档」，就报你电脑里现在真有的、打算让这个程序去查的那几份。

### 第 2 轮

**学生**：你觉得呢？LangGraph 还是 CrewAI，你帮我选一个呗。

**工具调用**：（一个都没有）

**教练**：

选 **LangGraph** —— 而且这个选择其实不由你我定，任务的交付物里已经白纸黑字写了：「能跑起来的代码，用到『LangGraph 状态图』里的东西」。选项已经被验收标准锁死了。

抛开这一层，技术上它也是对的，理由正是你这次要练的那两点：

- **「多智能体分工与状态传递」要练的是状态怎么传**，那状态就必须摆到台面上。LangGraph 里 state 是你自己声明的 schema，每个节点声明读哪个字段、写哪个字段、哪条边带什么过去——传递路径是显式的，你能在图上指着看。CrewAI 把这套东西包进了 crew/task 的高层抽象里，框架替你决定大部分传递方式，你练不到「传递」本身。
- **「参数传错要报错而不是瞎猜」靠的也是这个**：state 有类型约束，字段名拼错、该传的没传，图跑起来直接抛异常；状态是个无约束的 dict 时，传错了它照样往下走，这正是「瞎猜」的来源。

你的有效判断是**该按任务需求选工具，不看热度**——方向对。缺口是：你没给出任何依据就让我替你定，这等于把决定外包了。下次遇到同类问题，你该拿出来的就是上面那两条：一条对应交付物，一条对应验收标准。

1. **`graph.py:10` `StateGraph(dict)` —— 这是最要命的一处。** state 是个裸 `dict`，意味着任何字段名都能塞进去、传错了不会有任何声音。你的验收标准原话是「参数传错时会报错而不是瞎猜」，这个写法正好是反面：它保证了瞎猜。LangGraph 的 `StateGraph` 是可以接**带类型的 state 定义**的（TypedDict 或 Pydantic 都行），字段声明了，缺字段、类型不对才会在跑的时候炸出来。这条验收基本就押在这一行上。

```python
def plan(state):
    state["plan"].append("先查资料")
    return state

def build():
    g = StateGraph(dict)
    g.add_node("plan", plan)
    g.set_entry_point("plan")

```
