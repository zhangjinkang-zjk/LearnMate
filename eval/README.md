# 测试思路

这份文件写给两拨人：**要改这套评估的人**，和**要把它写进提交文档的人**。
它讲的是"为什么这么测"，不是"跑了哪些用例"—— 结果在 `results/`，且每次都不一样。

## 一、为什么单靠单元测试不够

`backend/tests` 那一千多条测的是**确定的逻辑**：给定输入，输出应该是什么。
它们跑得快、离线、退出码明确，是本项目的测试主干。

但有几类东西它测不到，而且不是"再多写几条"能补上的：

| 测不到的东西 | 为什么 | 谁测 |
|---|---|---|
| 教练**怎么说话**（像不像同行、会不会念表格） | 判据是主观的，没有断言可写 | `persona_eval.py` |
| 教练**怎么选工具**（该查的时候查不查） | 由模型在循环里自主决定 | `persona_eval.py` |
| 诊断**问得好不好**、路径**生成得合不合理** | 输出是开放的，没有唯一正确答案 | `journey.py` |
| 注册表里那几十个 URL **还能不能抓** | 依赖外网，且文档站会改版 | `backend/scripts/check_framework_docs.py` |

这些的共同点是：**被测对象是模型，输出是采样出来的**。所以这套评估不能给出"通过/失败"，
它给出的是**通过率和判官的理由** —— 用来发现问题和看趋势，不用来卡 CI（见第六节）。

上面这张表回答的是"单元测试测不到什么"，没回答"这套评估自己该覆盖到什么"。下一节把
"测什么"按四类能力摊开 —— 今天的覆盖是不均的，其中一类**一条判据都还没有**。

### 单元测试那一层（`backend/tests`）

写这份时的规模：**79 个文件 / 833 个用例**（含参数化，pytest 报 1303 条），全量跑完约 20 秒。

```bash
$PY -m pytest backend/tests -q
```

它的写法有三条约定，加新用例时照着来：

- **离线、不连库、不联网。** 需要外部依赖的地方就地造一份假的 —— 46 / 79 个文件用
  `monkeypatch`，连那几个 import 了数据库层的文件也都是把 `init_db` 换掉，不是真调。
  `conftest.py` 因此只有两个 fixture（事件循环、临时音频目录），没有共享的数据库 fixture。
  一条要联网或要连库才能跑的用例，等于一条多数人跑不了的用例。
- **文件名就是它守的那件事**：`test_diagnosis_feedback_reaches_the_student.py`、
  `test_llm_key_matches_endpoint.py`、`test_direction_is_real_or_absent.py`。
  读名字该知道它在防什么回归，不用点进去。
- **开头写清"这条测试守的是什么 bug"**（74 / 79 个文件有）。尤其是那种看起来多余、
  删了也不会有测试失败的用例 —— 它守的往往是一次真实事故。**那段说明是它唯一的辩护。**

和上面四类的分工很简单：**确定逻辑进这里，模型行为进 eval。**
一条断言写得出确定期望值的用例，不该放进评估去花模型调用。

## 二、要盯的四类能力

"测什么"按四类能力摊开，每类写清**怎么测、看哪个产物、什么算不合格**。
四类的覆盖是不均的：第一类**今天一条都没有**，第二、四类只有很弱的信号。

### 能力一、领域知识的准确与可溯源（今天完全没有测量 —— 待补）

**为什么没有。** `persona_eval.py` 判的是话术（像不像同行、有没有念表格），
`journey.py` 把生成物照抄成 markdown —— 两者都没有一条判据去问"它写的这个结论对不对"。
一份排版漂亮、口吻像同行、但把某个 API 的用法讲反了的 PPT，现在全会绿。

**怎么测。** 补法分三步：

1. **从生成物里抽断言。** 只抽"可核验的"那种：具体 API 名与调用签名、版本号、公式、
   参数默认值、算法步骤、术语定义。每条断言带着它的出处（哪份资源、哪一节、原句），
   不是一句转述过的总结。
2. **和权威来源比对，来源分三层。** 最高一层是官方文档 / 规范 —— 用现成的
   `fetch_framework_docs`、`read_web_page` 把正文拉回来；中间一层是后端已入库的知识库；
   最低一层是通用模型自身的领域知识，**只用它把可疑项筛出来，不用它下判决**。对每条断言
   给出"被来源支持 / 被来源反驳 / 来源里查不到"三种结论之一。
3. **记录来源。** 每条断言在产物里带一个"来源格"：来源 URL 或文档 id、定位到节 / 段、
   比对结论。和转录必须落盘是同一条道理 —— **判词要能对证**，对不了证的断言等于没测。

**指标名**（只报指标，不给门槛）：领域知识谬误率（被来源反驳的断言 / 抽出的断言，按资源
类型分列）、断言可溯源率（带来源格且来源可复现的断言 / 抽出的断言）、来源缺失断言数。

**什么算不合格。** 出现被权威来源**直接反驳**的断言（是"来源里说的和它相反"，不是
"来源里查不到"）；或者一条断言没有来源格、却已经进了给学生看的产物。

### 能力二、画像 → 资源适配

**今天的弱信号。** `journey.py` 的 `_paths` / `_resources` 只读 `node_count`、`difficulty`、
`difficulty_score` 这些**声明的字段**。它看得出"有几个节点、难度字段写了什么"，看不出
"同一个知识点，对不同底子的人是不是真的换了讲法"。要测的是后者。

**怎么测。** 固定一个知识点，让两组底子明显不同的画像（比如"看过文档没写过"和"写过完整
项目"）各走一遍同一门课，取到同一知识点的资源（文档 / PPT 那一节），逐维度对比。对比全
落在产物**正文**上，不看它自称的难度：术语密度（每百字里没解释的专业名词）、先定义还是
先给例子（结构顺序）、例子贴不贴画像里的专业与年级、用到的前置知识是不是画像声明会的、
小节长度。

**指标名**：同知识点跨画像差异化率（在哪些维度上两组产物确实不一样）、画像-资源难度适配
一致率（资源用到的前置知识落在画像声明会的东西里的比例）、画像引用具体度（正文引到画像
具体信息的条数）。

**什么算不合格。** 底子差很多的两组画像拿到的是同一份内容 —— 同知识点在结构、例子、术语
密度上完全一致；或者资源里的前置知识超出画像声明的底子。

**一个实例。** 实测 4 条路径里有 3 条是同一份内容（"机器学习与深度学习"那条 15 个节点里
0 个机器学习节点），根因是大纲那一步把"学习目标"当成了改写整条路径的依据。今天这版 eval
只会把这三条照抄进报告 —— 它没有一条判据会指出"它们其实是同一份"。

### 能力三、多角色审核是否真的执行

审核角色由 `agent_names.py` 定义（内容审核智能体、交叉验证智能体，以及每种资源类型派生
出的审核角色）。要测的不是"审核说了什么"，而是**审核到底跑没跑**。两条链路都有"故障放行"：
审核没跑成时，对外的记录和"审核通过"长得一样。

**故障放行的形态**（写清这个，判据才能落地）：

- **路径链**：`path_graph.reviewer_node` 在 `except` 里返回 `review_passed=True`，同时把
  `review_source` 置成 `"error"`。正常审核通过是 `review_source="llm"`，无节点可审是
  `"skipped"`。**只有 `review_source` 能把"故障放行"和"真的通过"分开** —— 光看
  `review_passed`，两者都是 `True`。
- **资源链**：逐资源类型的 reviewer 在 `except` 里返回
  `{"passed": True, "score": 0, "feedback": "审核异常: ..."}`；PPT 的逐章节审核
  （`_review_ppt_section`）异常时是同一个形状。**这里连 `review_source` 都没有**，
  能认出来的只有 `score=0` 配 `passed=True`、feedback 前缀"审核异常"、以及推给前端的
  审核事件状态是 `failed`。
- **落库侧**：`GeneratedResource.review_passed` 是整条资源图 `review_passed` 的**聚合**。
  ppt / document / case / reading 是在生成阶段逐章节审核的，全局 reviewer 对它们直接返回
  `passed=True, score=100` —— 也就是说**章节级的故障放行不进这个聚合**，落库字段看不出来。

**怎么测、看哪个产物。** 判据要把每个审核单元的结论分成三态：**跑过且通过**、**跑过但
没通过**、**根本没跑成**。第三态现在容易被混进第一态，所以它要单独计数并逐条列出（哪条
路径 / 哪个资源、当时的 `feedback`）。路径看 `review_source`，资源看 `score=0 且 passed=True`
或审核事件 `failed`，PPT 章节再看那条 `[PPT-Review] section=... 审核异常` 的日志。

**指标名**：审核实际执行率（`review_source="llm"` 的路径 / 生成的路径；逐资源类型统计
"真跑过"的资源 / 生成的资源）、故障放行清单（逐条，含定位与当时的 feedback）。

**什么算不合格。** 一条路径 / 资源的对外结论是"通过"，而它对应的审核调用抛过异常
（`review_source != "llm"`，或审核记录里是异常形状）。这种必须在报告里逐条标出来，
不能混进"通过"。

**两个实例。** 实测 13 章 PPT 里有 2 章走了异常路径；还有一次路径审核因为回复里一个非法
JSON 转义（`1.5\~2.18`，波浪号前多一个反斜杠）整个作废 —— 后者正好演示了放行的下游：
审核没跑成，路径照样被放行，`review_passed` 仍是 `True`。

### 能力四、用例覆盖

**今天的量。** 1 个合成画像（`journey.py` 的 `STUDENT_PROFILE`）、1 条链路（诊断 → 方向 →
路径）、3 个教练场景（`scenarios.py`）。不够，而且缺的正好让上面三类测不出东西。

**要补什么。**

- **多组差异化画像**：至少两档、且底子差得开，让第二类有可比的两组。画像的差异要落在
  模型真能读到的字段上（会什么、不会什么、专业、年级）。
- **多个场景。** 教练那条每个场景挑一种顶法（现有三个：跳步、要登记表外的资料、文件没给
  看），补的场景继续挑没覆盖的顶法。path / resource 那条要多换几个领域。
- **多领域。** 生成和审核是逐领域跑的，只在一个领域上跑，看不到"换个领域知识就错"。
- **三段可读。** 每条用例的产物要能读出：**输入画像**（谁、什么底子、什么目标）、
  **中间决策**（诊断问了什么、大纲 / 审核各判了什么、哪一步把方向改了）、**最终资源**
  （生成物的正文和它的来源格）。现在 `journey.py` 的报告有前两段和一份资源清单，但资源
  正文和审核来源没进报告 —— 用例要能读出东西，得先把这三段落进报告。

**指标名**：画像组数、领域数、场景数、产物完整度（三段齐全的用例数 / 全部用例数）。

**什么算不合格。** 所有用例共用一个画像或一个领域（测出来的是"这套提示词在这一个点上
成立"）；产物里读不出中间决策（只剩最终资源，没法判断它是被哪一步定成这样的）。

## 三、一条贯穿始终的原则：走真的那条路

**受测的东西必须是真的。** 评估里跑的是一行行生产函数本身 ——
`stream_classroom_chat`、`diagnosis.service.start/answer`、`PathService.generate_subject_paths`——
不是它们的简化复刻。

这条原则不是洁癖，它是被一次真实事故定下来的：

> 早先那版评估为了不碰数据库，把教练的 persona 和工具表**从代码常量直接塞进 `Brain`**，
> 跳过了"从库里读这两样"的那一步。那版跑了几十遍都是绿的。
>
> 而 `service/agent/service._ALLOWED_TOOLS` 里少列了三个工具 —— 它是个静默过滤器，
> 新库上第一次创建教练时会把它们滤掉，教练只剩 5 / 8 个工具，而且进程内缓存让它
> 到后端重启为止都不会自愈。**这个 bug 就住在被跳过的那一步里，那版评估永远看不见它。**
>
> 改成走生产入口（`stream_classroom_chat`）之后，第一次跑就露了。

所以：**不要为了好测而绕开被测的那一步。** 需要方便，就把"方便"做在库和外部服务那一侧。

## 四、只固定"世界"，不固定被测对象

`fixtures.FIXED_WORLD` 换掉几个工具背后的返回值，工具的名字、描述、参数 schema
全部保持生产原样 —— 模型看到的工具表和生产完全一致，"该不该调、调哪个、参数怎么写"
全由它真决定。

固定世界只有三条理由，每条都得站得住才加：

1. **花钱。** `web_search` 走博查，按次计费。断言一次就是一次真金白银。
2. **不能动别人的库。** `search_knowledge_base` / `read_portrait` / `search_memory` /
   `get_used_history` 要读 MySQL。评估不该往生产库塞测试数据。
3. **不固定就不可比。** 搜索引擎每天返回的不一样，同一场景跑两遍得到两套对话，
   于是"这次比上次好"永远说不清是改动带来的还是世界变了。

**这几样不参与判分。** 判据判的是教练怎么说话、怎么选工具 —— 工具背后那份数据是布景。

## 五、几种具体做法，以及它们各自防的是什么

### 剧本里的学生发言是写死的

`scenarios.py` 里每一句学生发言都是手写的，不是让模型演的。

通用评估工具通常提供一个"合成用户"，但它造出来的是**正常用户** —— 不会故意说
「你觉得呢」「直接给我一段能贴的」。而教练的毛病恰恰只在被顶的时候才露头：
替他做决定、给现成答案、把学生推去站外。剧本要挑的就是这些顶法。

**需要模型演的地方要写清短板。** `journey.py` 里的诊断反过来必须有个假学生，
因为诊断是自适应的（「必须接住上一轮回答中的具体内容」），写死的答案接不住上一轮。
那个假学生的底子写在 `STUDENT_PROFILE` 里，并且**它的两处天生短板也写在文件开头** ——
模型扮初学者常会答得比真人好，所以那份记录看得出"生成得合不合理"，
看不出"对真人准不准"。**把评估的局限写在评估里**，不然读的人会当成结论。

### 判据抄自 persona 里的硬规矩

`persona_eval.py` 的每一条判据都能在 `prompts/classroom/coach.yaml` 里找到对应的规矩
（"永远别说'我们现在进入某阶段'""不给能直接粘进去的文字"…）。

**改 persona 时必须一起改判据。** 判据落后于 persona 的话，这个门禁守的就是一份过期的规范；
反过来，persona 删掉的规矩还留在判据里，就会稳定地误报。

判据要写得**近乎机械**（"加粗超过三处就不通过"），并且**把判官的理由打出来给人抽检** ——
只看分数会漏掉"理由明显不对但分数碰巧过线"的情况。

### 一轮不算数

模型回复是采样出来的，同一条判据在两次不同对话上的结论可以差很远（实测在 0.80 和 0.20
之间跳）。所以同一场景默认跑 3 轮，看**通过率**，不看单轮。单轮翻转不代表什么，
多数轮都不过才是真信号。

### 记录必须落盘

每次跑都把**每一段对话**写成 markdown（`results/<时间戳>-transcripts.md`），带每轮的
工具调用。第一版评估只把对话打一份到 stdout，九个桥里只有第一个场景的第一轮留了下来 ——
判词里写着"没调到 web_search"，却没有任何地方能点开看它当时到底调了什么。**判词要能对证。**

### 合成学生用完即弃

路线 A 需要库里真有一行用户。`subject.py` 每次跑建一个**只属于这个进程**的账号
（名字带 pid），跑完在 `finally` 里删干净。

- **为什么不是一个共享账号**：评估是并发跑的，共享账号的话先跑完的那个会把别人正在聊的用户删掉。
- **为什么每轮都要重建**：出过事的恰恰是**创建**那条分支，复用已有配置就绕开了它。
- **删不干净的地方**：`exam_questions` / `learning_paths` / `user_picture` 三张表的外键是
  `SET_NULL`，删用户**不会**带走它们，必须显式删 —— 漏掉就是每跑一次在别人库里留一整套孤儿。
- **安全锁**：删任何东西之前先确认用户名带 `coach-eval-` 前缀。真实用户名不会长这样。
- 崩在半路的账号用 `python eval/subject.py --list / --sweep` 收尾。

### 判据并发、剧本串行

- 判据之间彼此独立，**全放出去并发**（`MAX_CONCURRENT_JUDGE_CALLS`）。一条判据一次调用，
  串行跑纯粹是浪费。
- 剧本（桥）**一次只跑一个**（`MAX_CONCURRENT_BRIDGES`）。每个桥起来都要走一遍
  `init_db()`，也就是生产启动那套建表 + ALTER；九个桥同时对着同一个 MySQL 做 DDL 会互相抢
  元数据锁，实测直接死锁（`1213, Deadlock found when trying to get lock`）。
  那不是"重试一下就好"的错误 —— 往别人的库上并发发 DDL 本来就不该有。

## 六、不做什么

- **不进 CI。** 它要联网、要真实模型调用、要动数据库，而且结论是概率性的。
  卡 CI 的是 `backend/tests`。这套评估是**改动前后手动跑、读记录、看趋势**。
- **不追判官的分数。** 判官和被测是同一个模型，有"自己判自己"的盲区。所以判据写得近乎机械、
  理由打出来给人看。分数是线索，不是裁决。
- **不把固定世界当成果。** 固定是为了可比；真要验证"真世界下行不行"，
  把 `FIXED_WORLD` 里对应的键删掉即可，那个工具会退回生产实现（见 `coach_bridge`）。

## 七、怎么跑

```bash
# 环境：后端那个 conda 环境（zhiban）。DeepEval 现在也装在里面。
PY=F:/anaconda3/envs/zhiban/python.exe

# 教练行为评估：全部场景 × 3 轮，跑完判分
$PY eval/persona_eval.py
$PY eval/persona_eval.py skip-to-stack        # 只跑一个场景
$PY eval/persona_eval.py --runs 5             # 多跑几轮
$PY eval/persona_eval.py --raw                # 只打对话原文，不判分（便宜得多）

# 入学一程：诊断 → 方向拆解 → 路径生成（十几分钟，挂后台跑）
$PY eval/journey.py

# 合成账号残留
$PY eval/subject.py --list
$PY eval/subject.py --sweep

# 注册表里那些官方文档 URL 还抓不抓得到（联网）
$PY backend/scripts/check_framework_docs.py
```

产出一律落在 `eval/results/`：`<时间戳>.json` 是通过率汇总，`<时间戳>-transcripts.md`
是对话原文，`<时间戳>-journey.md` 是入学一程。**`results/` 是"改这个功能前后变了什么"的
唯一权威副本** —— 写文档时数字从那里取，别凭记忆（见 `docs/优化计划.md` 的口径附录）。

## 八、文件清单

| 文件 | 是什么 |
|---|---|
| `scenarios.py` | 教练评估的剧本：任务、学生发言、每轮工作区里有啥。纯数据 |

| `subject.py` | 合成学生：建、删、查残留 |
| `results/` | 每次跑的结果和对话原文 |
