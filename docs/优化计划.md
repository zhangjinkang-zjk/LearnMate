## 一、功能

### 1. 视频搜索（独立入口）

> **状态：后端双视频源 + 三档降级已完成，前端也已接上。** 视频走 **B 站官方搜索接口**（带 `buvid3` 指纹、熔断、相关性过滤），
> **课程平台的视频课程**与图文走**博查**。B 站被限流时自动退回博查，**不会没有视频**，只是从"站内播放"降级成"跳转播放"。
>
> 📄 **接口契约与现状在 [外部视频接入说明.md](外部视频接入说明.md)** ——
> 字段表、展示顺序、已知缺陷都在那边。本文件只留计划与实测记录，避免两处各写一份。

**改之前是什么样**

检索底层是 `backend/src/service/video/service.py` 的 `ExternalVideoService.search()`，
它直接打 `api.bilibili.com/x/web-interface/search/type`，只带了 `User-Agent` 和 `Referer`，
有三个雷：

1. **没有 wbi 签名、没有 `buvid3` cookie**。B 站 2023 年起给 web 接口加了 `w_rid` + `wts` 校验（要先请求 `nav` 拿 `img_key`/`sub_key`，按固定重排表混出 `mixin_key` 再 MD5），还会给未登录请求发指纹 cookie。这套裸调用**在开发机可能能用、在云服务器 IP 段大概率被风控挡**（B 站对机房 IP 特别敏感）。
2. **静默失败**：`except Exception: return []`。接口挂掉时前端只看到"没有推荐视频"，**根本排查不出是接口坏了**。
3. **没有任何限流**：它在资源生成链路里，用户每生成一次资源就打一次 B 站。

**已实现**（已用真实 API 跑通）

- [x] **不在代码里逆向 wbi**：视频走的是**不需要签名**的老接口 `x/web-interface/search/type`，带上 `buvid3` 指纹即可通。新接口 `x/web-interface/wbi/search/type` 会下发 `v_voucher` 验证挑战 —— **解不了也不去解**
- [x] **域名白名单落到 `backend/src/utils/education_sources.py`**，作为唯一事实来源（不是散在业务逻辑里的 `if`）
- [x] **白名单用博查的 `include` 参数在 API 层限定**，并在结果侧再按域名筛一遍兜底（`include` 只是请求侧建议，实测可能仍返回名单外站点）
- [x] **`_extract_bvid()` 只在解出 BV 号时才给 `embed_url`**，非 B 站来源和 b23.tv 短链一律留空
- [x] 失败可见：不再 `except: return []` 无声吞掉，日志会记录未配置 / 超时 / HTTP 状态码
- [x] 上游 `search_and_save()` 与 `_search_external_videos_early()` **一处未改**（返回结构保持不变）
- [x] **熔断**：被 412 / 429 或 `v_voucher` 拦下就静默 10 分钟（`BILIBILI_CIRCUIT_SECONDS`），期间直接走降级，**绝不继续打接口** —— 越打封得越久
- [x] **相关性过滤**：B 站接口**永远返回满页**，"返回了 N 条"是假信号。用本地 BGE 模型按余弦相似度筛一遍（`EXTERNAL_VIDEO_MIN_SIMILARITY`，默认 0.55），见下方「实测数据」
- [x] **双视频源 + 三档降级**：B 站取可站内播放的视频 → 课程平台（博查，**也是视频课程**，只是跳转播放）→ 图文（博查，只在没凑够条数时才查）。B 站**真的没拿到**时才动博查的 B 站档兜底。三档各查各的，**不混在一次查询里** —— 混查必被内容量大的站点挤光名额（这个坑犯了两次，见「实测数据」第 3 条）
- [x] **节点级接口**：`GET /path/{path_id}/node/{node_id}/external-videos`，检索词取自节点的 `knowledge_tags` 而**不是节点标题**
- [x] **明确不做**：轮换 `buvid3` 指纹去绕限流 —— 那是规避风控，性质不对

**实测踩到的两个坑（都已在代码里处理，别再踩回去）**

1. **B 站必须单独查一次。** 通用的网页搜索在 B 站返回的绝大多数是**图文专栏（`/read/`）、付费课程（`/cheese/`）、收藏夹（`/medialist/`）和旧格式 AV 号**——实测限定 `bilibili.com` 抓 20 条，真正的 `/video/BV` 页只有 2～6 条。所以把 B 站和十几个课程站点放在一次查询里时，B 站的名额会被挤光，**一条视频页都剩不下**。现在拆成两次查询（`include_domains("embed")` 与 `include_domains("course", "reading")`），B 站优先占位。（**2026-09-28 更新**：视频改由 B 站接口直接提供后，`embed` 那档已降级为「B 站没拿到时」的兜底；后来 `course` 和 `reading` 也拆开了 —— 见「实测数据」第 3 条。现在是 course / reading / embed **三档各查各的**。）
2. **只保留能播的单个视频页。** `embed` 档上只有 `/video/BVxxx` 算视频，其余一律丢弃；有 BV 号时把地址归一成 `https://www.bilibili.com/video/{bvid}`，顺带去掉 `m.` 移动域名和 `?from=search` 之类的尾巴，同一集的多个地址会因此被去重。

**实测数据（真实 API 跑的，不是推测）**

博查在 B 站视频上是**结构性召回失败**，换查询词救不回来：

| 查询 | 博查返回真视频 | B 站接口返回真视频 |
|---|---|---|
| `RAG 检索增强生成` | 0 / 20 | 20 / 20 |
| `上下文窗口 大模型` | 2 / 20 | 20 / 20 |
| `企业级RAG系统` | 0 / 20 | 20 / 20 |
| `线性代数 教程`（对照组） | 3 / 20 | 20 / 20 |

11 组查询（宽窄都有）用博查总共只捞到 **15 条**真视频页，平均 1.4 条；其余全是 `/read/` 专栏、`/cheese/` 付费课、`/medialist/` 收藏夹、`/opus/` 动态。原因是博查是**网页**搜索引擎：B 站视频页 JS 渲染、正文稀薄，索引质量天然差，永远排在有真实正文的专栏文章后面。**这不是查询词问题，是索引结构的差距。**

但 B 站接口有两个必须知道的坑：

1. **IP 级限流，而且会升级到全封。** 实测约 60 次请求后**全部 412**；换全新 `buvid3` 指纹照样 412、间隔拉到 3 秒、复用连接都一样 —— **封的是 IP 不是指纹**，且没有可预期的恢复时间。开发机因此被封过。生产服务器是另一个 IP、按低频调用大概率能用，但**不能把演示押在"希望它不封"上**，所以降级路径是必须的。也正因如此，**不做指纹轮换**（那是规避风控，性质不对，而且只会加速封禁）。
2. **相关性不稳定，"有结果"是假信号。** 接口**永远返回满页**，哪怕查询毫无意义。实测节点「分组聚合与结果导出」召回「origin合并两个文件」、「Service 层单元测试与数据隔离」召回「Cr2O3多壳层EXAFS拟合」。规律是：**行业通用概念名搜得到，我们自己编的教学式标题搜不到**。所以检索词改用节点的 `knowledge_tags`（`Token计数 上下文窗口`、`BM25原理 RRF融合`）—— 实测 1370 个节点**标签覆盖率 100%**，不会退回到那条差路径。残留风险是「课程导航」「学习目标拆解」这类元节点标签也是自造的，召回会差。

   相关性过滤的阈值是在 **16 组真实配对**上标定的：相关 0.348~0.778、不相关 0.385~0.541 —— **两个分布是重叠的**，不存在能干净分开的阈值。0.55 在这个样本上恰好精度 100%、召回 8/9，但最高不相关(0.541)与最低保留相关(0.548)只差 **0.007**，**这点余量是运气不是信号**，换个语料就会变。所以它是**偏精度**的过滤：宁可漏掉几条好的，也不要在学习页上推 EXAFS 拟合。嫌严就把 `EXTERNAL_VIDEO_MIN_SIMILARITY` 调低（0 = 不过滤）。

3. **课程平台的名额被图文挤光了（已修）。** 把 `course` 和 `reading` 放进**同一次** `include` 时，返回的 20 条**全是掘金文章** —— 中国大学MOOC / 学堂在线 / 智慧教育平台 / 网易公开课 / 慕课网 **一条都没有**；单独查 `course` 那一档则是 **20 条全慕课网**，且全部切题（大模型应用开发、LangChain、LLM 入门）。**这和 B 站那次是同一个病**：名额被内容量更大的站点挤光。现在 `course` 单独查，`reading` 只在没凑够条数时才查（顺带省一次付费调用，常见情况仍是 1 次）。**这条最该记牢**：我们一开始以为「博查搜不到课程」，其实是自己把课程和图文塞进了一次查询。

**合规来源白名单**（实现在 `backend/src/utils/education_sources.py`）

### 2. 「交代码」入口（结合应用实践模块）

> **⚠️ 这一条的前置条件在 2026-09-30 变了。** 提交与判分**已经整体删除** —— 阶段机、`[[PHASE:done]]` 标记、确定性基线 + LLM 复核、`POST .../sessions/{id}/submit`、前端 `submitPracticeSession`，全部不在了。
>
> 删的原因不是"多余"而是**有害**：删除前没有任何界面在读那些结果（提交入口早就没了），而它们留下的阶段文案会随会话历史回放给模型，让教练一直追一个**已经不存在的议程** —— 学生问「看看我的代码」，它回「我们先完成「定义交付」这一步」。判分本身也站不住：一条同时含「依据/验证/方案」的消息就能到 60 分通过线，它量的不是方案好坏，是有没有出现这几个词。
>

## 四、检索架构（RAG）

**现状链路**：文件 → 提取文本 → 按 **700 字**切块（80 字重叠）→ 每块算一个向量 → 向量以 **base64 编码的 float32 裸字节**存进 MySQL 的 `knowledge_vectors.embedding` → 检索时把**全表**拉进 Python 算余弦、排序取 top_k → 拼成一段纯文本返回。

先说实话：**现在语料只有几百段（公共 342 + 私有 176），全表扫描还跑得动**。所以下面这批改造，一半是为了**上量不崩**，一半是因为这套架构在答辩时站不住。

> **2026-09-30 更新：RAG-A 与 RAG-B 的主干已经做完了**，下面保留的是当时的分析（它解释了为什么是 700/80、为什么必须换模型）。**还没做的是评测基线、向量库索引、混合检索、rerank。**
>
> 当前事实（已核实）：
> - 嵌入模型是 **`BAAI/bge-m3`**（1024 维、8192 token 窗口），规格与切换方式见 [`系统设计.md` 第 11 章](./系统设计.md)。**不是** `bge-small-zh-v1.5` 了 —— 别按旧的讲。
> - 切块 **700 字 / 重叠 80 字**，尺寸**跟着模型规格走**（`utils/embeddings/registry.py` 的 `chunk_max_chars` / `chunk_overlap_chars`），入库路径显式传入。700 的实测依据：本库语料 tokenizer 是 XLMRobertaTokenizer、**token/字符 = 0.508**，700 字 ≈ 333 token、最长实测 552，落在推荐的 400~512 token 带附近。
> - 向量是 **base64 float32 裸字节**，不是 JSON（`unpack` 兼容首字符为 `[` 的旧 JSON 格式）。
> - 跨片上下文前缀**已经拆干净**：`apply_context_prefix`（`file_processor.py`）生成「上文摘要：…」只用于**编码**，入库的 `content` 是干净正文。以前它直接拼进 `content`，每段正文开头都带着前缀，页面上看得见、提示词里也带着。
>
> ⚠️ `registry.py` 里还有一句 docstring 指向已删除的 `file_processor._add_overlap`（现在叫 `apply_context_prefix`），纯注释残留。

### RAG-A 切割方法（已按此升级）

**当时的做法**：`chunk_text(text, max_chars=1000, overlap_chars=150)`，唯一调用点 `knowledge_router.py`。

**当时的真 bug**：切块 **1000 字**，而当时用的 `BAAI/bge-small-zh-v1.5` **最大 512 token**（约 500～700 汉字），模型 `config.json` 里 `max_position_embeddings: 512`，而全仓库**没有任何 `max_seq_length` 的设置**。结果**每块的向量只反映前半段**，后半段在检索时等于不存在 —— 能不能被检索到，取决于内容是不是恰好在块的开头。

**这一条已修**：换成 `bge-m3`（8192 窗口）后窗口不再是瓶颈，切块尺寸改为从模型规格取（模型规格里写 `chunk_max_chars`），不会再出现「块比窗口大」。

还有几条**当时就存在、现在仍在**的问题：

- **长文档尾部会产生被静默丢弃的碎片**：`<50` 字的 chunk 会被 `ingest` 直接拒绝（`knowledge_base.py`），调用方只计入 `skipped`，既不报错也不提示。
- **块内结构会被切碎**：按句子切分不认识代码块和表格，代码/表格可能被腰斩。
- **块与返回长度互相打架**：检索返回时按 `RAG_RESULT_MAX_CHARS`（默认 1200）截断，凑不齐完整小节。

**还没做的**

- [ ] 改成**按标题层级切**（Markdown 的 `#/##/###`、PDF 的章节），块内保留完整小节，而不是纯粹按字数
- [ ] **父子块（small-to-big）**：用小块做检索、命中后把它所属的**整个小节**喂给模型 —— 兼顾检索精度和上下文完整
- [ ] 代码块、表格**不切**
- [ ] 改完**必须重建全部向量**（`scripts/reembed_all.py --apply`）

### RAG-B 换 embedding 模型（已完成）

**当时用的是** `BAAI/bge-small-zh-v1.5` —— BGE 系列里**最小的一档**（约 24M 参数、512 维、512 token 窗口），2023 年版本。

| 模型 | 维度 | 窗口 | 特点 |
|---|---|---|---|
| `bge-small-zh-v1.5`（**当时用的**） | 512 | 512 token | 小、快，但中文语义和长文本都弱 |
| `bge-large-zh-v1.5` | 1024 | 512 token | 中文效果明显更好，窗口没变 |
| **`bge-m3`（现已采用）** | 1024 | **8192 token** | 多语言 + 长窗口 + 同时支持 dense / sparse / 多向量输出 |
| `bge-reranker-v2-m3` | — | — | reranker 侧配套（见 RAG-F） |

**选它的三个理由**（都兑现了）：长窗口 8192 让切块 bug 消失；自带 sparse 输出可以当将来混合检索的关键词一路；多语言。

**做的时候踩到的（留作记录）**

- **换模型 = 全量重建向量**。维度 512 → 1024，旧向量全部作废，必须 `scripts/reembed_all.py --apply` 重嵌一遍。
- **国内拉模型**：靠 `HF_ENDPOINT`（默认 `https://hf-mirror.com`）或**把权重预置到 `backend/embedding_models/<slug>`** —— 后者已经在做（`BAAI__bge-m3` 就在仓库里）。
- **启动期拉模型不再是硬失败**（2026-09-30 纠正）：`main.py` 的预加载**已经有 try/except**，失败只记日志并把检索降级，**其余功能照常服务**。旧文档写的「`await` 且没有 try/except，拉不到模型 = 后端起不来」**已经不成立**。
- 模型体积约 2 GB 级，注意服务器磁盘与镜像大小。
- **可插拔**：`EMBEDDING_MODELS` 规格表 + 环境变量 `EMBEDDING_MODEL_ID`；未知模型 `resolve()` 直接报错，不静默回退。

### RAG-C 向量库怎么选

**现状**：向量以 **base64 编码的 float32 裸字节**存在 MySQL 的 `knowledge_vectors.embedding`，检索时把全表拉进 Python，逐条反序列化再算点积 —— **没有任何 ANN 索引**（早期是 JSON 文本，比二进制大 3～4 倍，已改）。

| 候选 | 形态 | 适合我们的理由 / 代价 |
|---|---|---|
| **FAISS**（建议先上） | 进程内库 | 纯 CPU、**不用新增服务、不用改数据流**；几百～几万段完全够。代价：索引在多进程下要各自加载 |
| Qdrant | 独立服务 | 运维友好、原生支持元数据过滤；要新增一个容器 |
| Milvus | 独立服务 | 功能全但重，得等语料上到十万级才值 |
| Redis Stack | 复用现有 Redis | 已经有 Redis，换 `redis-stack` 镜像即可走 RediSearch 向量索引；代价：镜像换了、内存占用上去 |
| pgvector | 换数据库 | 要从 MySQL 迁到 PostgreSQL，代价最大 |

- [ ] 建议：**先 FAISS**（不新增服务、不改数据流），向量存二进制，`doc_id` 与 MySQL 一一对应
- [ ] 职责分开：MySQL 存正文与元数据，向量侧只存 `doc_id` + 向量
- [ ] 语料上量后再评估要不要换成 Qdrant

### RAG-D 调用方式

**现状**：一个函数 `search(query, top_k, user_id, category)`，**返回拼好的纯文本字符串**，被 6 个地方直接 `await`：

| 调用点 | 传什么 | 影响 |
|---|---|---|
| `ai_core/resource_graph.py:827, 1490` | `f"{topic} {section_title}"`, top_k=3 | **在 section 循环里 —— 每生成一节就查一次**，一篇 6 节的讲义 = 6 次全表扫描 |
| `ai_core/tools/knowledge.py:257` | 模型自己给的 query | 作为智能体工具被 LLM 调用 |
| `service/path/service.py:240, 574` | `subject`, top_k=5 | 生成学习路径时按科目查 |
| `service/resource/generation_context.py:131` | `topic`, top_k=3 | 资源生成上下文，与主流程并发 |
| `service/mock_classroom/service.py:271` | query, top_k=5 | 模拟课堂评分时取依据 |

问题：

- **返回字符串** → 调用方拿不到结构化结果，**没法做引用、重排、去重**，只能整段塞进提示词
- **讲义生成是"每节查一次"**，是全表扫描的性能放大器（代码里那个 `RAG_GLOBAL_SEARCH_CONCURRENCY=20` 的全局信号量，其实就是在给这件事踩刹车）
- **参数散落**：top_k 有的 3 有的 5、`category` 几乎没人传、重复主题每次都重算

**升级方向**

- [ ] 统一成 `retrieve(query, *, top_k, user_id, categories, mode)`，返回**结构化 `list[dict]`**（doc_id / 标题路径 / 分数 / 正文），文本拼接交给调用方
- [ ] 加批量入口 `retrieve_many(queries)`：讲义生成**一次扫描覆盖整篇多节**，而不是循环里查 N 次
- [ ] 检索结果加缓存（query + 用户可见范围做 key），同一主题重复生成时直接命中
- [ ] 把 `RAG_*` 参数收进统一的配置模块，别再散在 `os.getenv`

## 附：已核实的口径（别再凭印象说）
