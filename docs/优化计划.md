## 一、功能

### 1. 视频搜索（独立入口）

> **状态：后端已换血**（B 站裸接口爬虫已删除，改走博查 + 教育来源白名单）。
> **前端仍未接播放** —— 见下方「已实现 / 未实现」。

**改之前是什么样**

检索底层是 `backend/src/service/video/service.py` 的 `ExternalVideoService.search()`，
它直接打 `api.bilibili.com/x/web-interface/search/type`，只带了 `User-Agent` 和 `Referer`，
有三个雷：

1. **没有 wbi 签名、没有 `buvid3` cookie**。B 站 2023 年起给 web 接口加了 `w_rid` + `wts` 校验（要先请求 `nav` 拿 `img_key`/`sub_key`，按固定重排表混出 `mixin_key` 再 MD5），还会给未登录请求发指纹 cookie。这套裸调用**在开发机可能能用、在云服务器 IP 段大概率被风控挡**（B 站对机房 IP 特别敏感）。
2. **静默失败**：`except Exception: return []`。接口挂掉时前端只看到"没有推荐视频"，**根本排查不出是接口坏了**。
3. **没有任何限流**：它在资源生成链路里，用户每生成一次资源就打一次 B 站。

**已实现**（已用真实 API 跑通）

- [x] **不在代码里逆向 wbi**：改走博查（见「五、联网搜索」），风控与签名交给服务商
- [x] **域名白名单落到 `backend/src/utils/education_sources.py`**，作为唯一事实来源（不是散在业务逻辑里的 `if`）
- [x] **白名单用博查的 `include` 参数在 API 层限定**，并在结果侧再按域名筛一遍兜底（`include` 只是请求侧建议，实测可能仍返回名单外站点）
- [x] **`_extract_bvid()` 只在解出 BV 号时才给 `embed_url`**，非 B 站来源和 b23.tv 短链一律留空
- [x] 失败可见：不再 `except: return []` 无声吞掉，日志会记录未配置 / 超时 / HTTP 状态码
- [x] 上游 `search_and_save()` 与 `_search_external_videos_early()` **一处未改**（返回结构保持不变）

**实测踩到的两个坑（都已在代码里处理，别再踩回去）**

1. **B 站必须单独查一次。** 通用的网页搜索在 B 站返回的绝大多数是**图文专栏（`/read/`）、付费课程（`/cheese/`）、收藏夹（`/medialist/`）和旧格式 AV 号**——实测限定 `bilibili.com` 抓 20 条，真正的 `/video/BV` 页只有 2～6 条。所以把 B 站和十几个课程站点放在一次查询里时，B 站的名额会被挤光，**一条视频页都剩不下**。现在拆成两次查询（`include_domains("embed")` 与 `include_domains("course", "reading")`），B 站优先占位。
2. **只保留能播的单个视频页。** `embed` 档上只有 `/video/BVxxx` 算视频，其余一律丢弃；有 BV 号时把地址归一成 `https://www.bilibili.com/video/{bvid}`，顺带去掉 `m.` 移动域名和 `?from=search` 之类的尾巴，同一集的多个地址会因此被去重。

**还没做**

- [ ] **前端内嵌播放**：全仓 grep 确认前端**从不读** `embed_url` / `cover_url` / `preview_url`，资源库视频卡片只渲染标题 / 来源 / 日期，「打开」弹的是**纯文字摘要** —— 内嵌播放**从来没接上**
- [ ] 独立的搜索入口 + 结果列表页（搜索框、结果卡片、播放/跳转）
- [ ] **博查不返回视频封面、时长、播放量**（只有站点 favicon）。当前无影响（前端不渲染这些字段），但做上方两条时会是缺失项，要么接受、要么另找数据源
- [ ] 检索结果纳入资源库的更细分类（现在只按 `external_video` 归到「视频」）

**合规来源白名单**（实现在 `backend/src/utils/education_sources.py`）

关键设计：**一个搜索 API + 一张域名白名单**，而不是 N 个爬虫。各家教育平台**都没有开放搜索 API**，自己爬等于把上面三个雷复制 N 份；搜索 API 一次调用拿回结果，按域名过滤即可，成本为零。

| 档 | 站点 | 域名 | 渲染方式 |
|---|---|---|---|
| A | B 站 | `bilibili.com`、`b23.tv` | **内嵌**：`player.bilibili.com/player.html?bvid=` 官方外链播放器（b23.tv 短链解不出 BV 号，退化成跳转） |
| B | 国家智慧教育平台（**教育部官方**，聚合中小学 / 高等教育 / 职业教育） | `smartedu.cn`（覆盖 `higher.` / `basic.` 子域）、`nvic.com.cn` | 跳转 |
| B | 中国大学 MOOC（网易 + 高教社） | `icourse163.org` | 跳转 |
| B | 学堂在线（清华发起） | `xuetangx.com` | 跳转 |
| B | 网易公开课 | `open.163.com` | 跳转 |
| B | 慕课网 | `imooc.com` | 跳转 |
| C | 图文参考 | `developer.mozilla.org`、`runoob.com`、`juejin.cn`、`github.com`、`arxiv.org` | 跳转 |

- 共 13 个域名，远低于博查 `include` 的上限（文档称 100，一说 20）
- **只有 A 档能嵌播放**。B 站外链播放器对**版权受限内容会拒绝播放**，接前端时要准备"该视频不支持站外播放，点此跳转"的兜底
- iframe 要加 `referrerpolicy="no-referrer"`，否则部分浏览器会拦
- **腾讯课堂已于 2024-10-01 正式停止运营，不要写进白名单**

**红线**

- 不下载 / 不转存任何视频文件，**只存元数据 + 外链**
- 不逆向签名、不绕过任何平台的风控或权限校验

## 四、检索架构（RAG）

**现状链路**：文件 → 提取文本 → 按 **1000 字**切块（150 字重叠）→ 每块算一个向量 → 向量以 **JSON 文本**存进 MySQL 的 `knowledge_vectors.embedding` → 检索时把**全表**拉进 Python 算余弦、排序取 top_k → 拼成一段纯文本返回。

先说实话：**现在语料只有几百段（公共 342 + 私有 176），全表扫描还跑得动**。所以下面这批改造，一半是为了**上量不崩**，一半是因为这套架构在答辩时站不住。其中 RAG-1 是**真 bug**，RAG-2 是**效果提升最直接**的一条。

### RAG-A 切割方法（含一个真 bug）

**现在的做法**（`backend/src/utils/file_processor.py:66`）：

```python
chunk_text(text, max_chars=1000, overlap_chars=150)
# 保留标题路径 → 按段落聚合 → 超长段落再按句子切 → 相邻块补 150 字 overlap
```

方法本身不算差（有标题路径、有重叠、不是粗暴按字长截断）。问题出在**参数和下游不匹配**：

- **bug**：切块是 **1000 字**，而入库用的 `BAAI/bge-small-zh-v1.5` **默认最大 512 token**（约 500～700 汉字），代码里**没有设置 `max_seq_length`**。结果：**每块的向量只反映前半段**，后半段在检索时等于不存在 —— 能不能被检索到，取决于内容是不是恰好在块的开头。
- **块内结构会被切碎**：按句子切分不认识代码块和表格，代码/表格可能被腰斩。
- **块与返回长度互相打架**：块 1000 字，但检索返回时又按 `RAG_RESULT_MAX_CHARS=1200` 截断，凑不齐完整小节。

**升级方向**

- [ ] 块长按**模型窗口**定，别拍脑袋：`max_chars ≈ 窗口 × 0.8`（bge-small 512 token → 约 400 字；换 `bge-m3` 后可以放到 1000+）
- [ ] 改成**按标题层级切**（Markdown 的 `#/##/###`、PDF 的章节），块内保留完整小节，而不是纯粹按字数
- [ ] **父子块（small-to-big）**：用小块（约 300 字）做检索、命中后把它所属的**整个小节**喂给模型 —— 兼顾检索精度和上下文完整，对"按小节生成讲义"这种场景特别值
- [ ] 代码块、表格**不切**
- [ ] 改完**必须重建全部向量**（否则新旧混存，见 RAG-H）

### RAG-B 换掉现在的 embedding 模型（最该换的一环）

**现状**：用的是 `BAAI/bge-small-zh-v1.5` —— BGE 系列里**最小的一档**（约 24M 参数、512 维、**512 token 窗口**），而且是 2023 年的版本。企业里做中文 RAG 现在普遍用 `bge-m3` 或 `bge-large-zh` 这个量级，差得确实不是一点。

| 模型 | 维度 | 窗口 | 特点 |
|---|---|---|---|
| `bge-small-zh-v1.5`（**现在用的**） | 512 | 512 token | 小、快，但中文语义和长文本都弱 |
| `bge-large-zh-v1.5` | 1024 | 512 token | 中文效果明显更好，窗口没变 |
| **`bge-m3`（建议）** | 1024 | **8192 token** | **多语言 + 长窗口 + 同时输出 dense / sparse / 多向量**，目前中文 RAG 的主流选择 |
| `bge-reranker-v2-m3` | — | — | reranker 侧配套（见 RAG-F） |

**为什么建议 `bge-m3`** —— 一次解决三件事：

1. **长窗口 8192**：RAG-A 的切块 bug 直接消失（1000 字的块不再是问题，甚至可以直接按小节切）
2. **自带 sparse 输出**：正好当 RAG-E 混合检索的**关键词一路**，不用再单独接 BM25 —— 一举两得
3. **多语言**：以后要接英文资料、或者企业语料是中英混排的，不用再换一次

**代价（必须说清楚）**

- [ ] **换模型 = 全量重建向量**。维度从 512 变 1024，旧向量**全部作废**，必须重新嵌入一遍（`knowledge_vectors` 全表）。这正好会踩到 RAG-H 的"静默丢向量"，所以**先修 RAG-H 再换模型**
- [ ] **服务器没有 GPU**。`bge-m3` 在 CPU 上比 `bge-small` 慢不少：批量入库可以离线慢慢做，但**单次检索的编码延迟**要实测；如果不可接受，退一档用 `bge-large-zh-v1.5` + MySQL 全文索引提供关键词一路
- [ ] **国内拉模型的问题**：现在 `_get_embed_model_async()` 本地目录没有就去 HuggingFace 直连下载，而 `main.py` 启动时会 `await` 它且**没有 try/except** —— 拉不到模型 = 后端起不来。换模型要么走 HF 镜像，要么**把模型文件预置到 `backend/src/ai_core/knowledge_base/` 下**再启动
- [ ] 模型文件体积：`bge-m3` 约 2 GB 级，注意服务器磁盘和镜像大小

### RAG-C 向量库怎么选

**现状**：向量以 **JSON 文本**存在 MySQL 的 `knowledge_vectors.embedding`，检索时把全表拉进 Python，`json.loads` 逐条反序列化再算点积 —— **没有任何 ANN 索引**，而且 JSON 比二进制大 3～4 倍。

| 候选 | 形态 | 适合我们的理由 / 代价 |
|---|---|---|
| **FAISS**（建议先上） | 进程内库 | 纯 CPU、**不用新增服务、不用改数据流**；几百～几万段完全够。代价：索引在多进程下要各自加载 |
| Qdrant | 独立服务 | 运维友好、原生支持元数据过滤；要新增一个容器 |
| Milvus | 独立服务 | 功能全但重，得等语料上到十万级才值 |
| Redis Stack | 复用现有 Redis | 已经有 Redis，换 `redis-stack` 镜像即可走 RediSearch 向量索引；代价：镜像换了、内存占用上去 |
| pgvector | 换数据库 | 要从 MySQL 迁到 PostgreSQL，代价最大 |

- [ ] 建议：**先 FAISS**（不新增服务、不改数据流），向量存二进制，`doc_id` 与 MySQL 一一对应
- [ ] 职责分开：MySQL 存正文与元数据，向量侧只存 `doc_id` + 向量
- [ ] 语料上量后再评估要不要换成 Qdrant

### RAG-D 调用方式

**现状**：一个函数 `search(query, top_k, user_id, category)`，**返回拼好的纯文本字符串**，被 6 个地方直接 `await`：

| 调用点 | 传什么 | 影响 |
|---|---|---|
| `ai_core/resource_graph.py:827, 1490` | `f"{topic} {section_title}"`, top_k=3 | **在 section 循环里 —— 每生成一节就查一次**，一篇 6 节的讲义 = 6 次全表扫描 |
| `ai_core/tools/knowledge.py:257` | 模型自己给的 query | 作为智能体工具被 LLM 调用 |
| `service/path/service.py:240, 574` | `subject`, top_k=5 | 生成学习路径时按科目查 |
| `service/resource/generation_context.py:131` | `topic`, top_k=3 | 资源生成上下文，与主流程并发 |
| `service/mock_classroom/service.py:271` | query, top_k=5 | 模拟课堂评分时取依据 |

问题：

- **返回字符串** → 调用方拿不到结构化结果，**没法做引用、重排、去重**，只能整段塞进提示词
- **讲义生成是"每节查一次"**，是全表扫描的性能放大器（代码里那个 `RAG_GLOBAL_SEARCH_CONCURRENCY=20` 的全局信号量，其实就是在给这件事踩刹车）
- **参数散落**：top_k 有的 3 有的 5、`category` 几乎没人传、重复主题每次都重算

**升级方向**

- [ ] 统一成 `retrieve(query, *, top_k, user_id, categories, mode)`，返回**结构化 `list[dict]`**（doc_id / 标题路径 / 分数 / 正文），文本拼接交给调用方
- [ ] 加批量入口 `retrieve_many(queries)`：讲义生成**一次扫描覆盖整篇多节**，而不是循环里查 N 次
- [ ] 检索结果加缓存（query + 用户可见范围做 key），同一主题重复生成时直接命中
- [ ] 把 `RAG_*` 参数收进统一的配置模块，别再散在 `os.getenv`

### RAG-E 混合检索：向量 + 关键词

- **现状**：纯语义向量一路到底。对**专有名词、API 名、版本号、编号**召回很差（`code2session`、`langgraph`、`v1.0.5` 这类），而"智能体开发"这套语料**满篇都是**。
- [ ] 加关键词一路：MySQL 全文索引（`ngram` 解析器支持中文）或 jieba + BM25
- [ ] 两路结果用 **RRF（倒数排名融合）** 合并，权重留配置
- [ ] 这条**对效果提升最直接**，建议排在换向量库之前

### RAG-F 加 rerank

- **现状**：没有。一次向量召回直接定生死，排在第 7 位的正确文档永远进不了上下文。
- [ ] 召回放大到 top-20 → `bge-reranker-base` 重排 → 取 top-5（CPU 可跑）
- [ ] 用 rerank 分数定阈值，替换现在形同虚设的 `RAG_MIN_SCORE`

### RAG-G 查询侧与结果侧

- **现状**：用户口语化的提问**直接拿去检索**；`RAG_MIN_SCORE` **默认 0.0**（等于不过滤，任何问题都会返回 top_k，不相关内容照塞进提示词 —— 幻觉来源之一）；返回的是**一整段拼接文本**，不带结构化引用。
- [ ] 查询改写 / 多查询：一句问话扩成 2～3 个检索式再融合
- [ ] `RAG_MIN_SCORE` 调到有意义的区间，**宁可返回"没检索到"，也别硬塞**
- [ ] 返回结构化引用：`doc_id` + 标题路径 + 相似度，前端能标出处、能溯源
- [ ] 元数据过滤与加权：`category`、知识点标签

### RAG-H 顺带修：维度不匹配被静默丢弃

- **现状**：`knowledge_base.py` 里 `if vec.shape != query_vec.shape: continue` —— 维度不一致的向量**无声跳过**。换模型或新旧向量混存时，检索结果会**悄悄变少**，而且完全排查不出来。
- [ ] 改成：告警日志 + 标记该条"待重嵌入"，让问题可见
