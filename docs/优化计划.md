## 一、功能

### 1. 视频搜索（独立入口）

> **状态：后端已是双源 + 降级** —— 视频走 **B 站官方搜索接口**（带 `buvid3` 指纹、熔断、相关性过滤），
> 课程平台与图文走**博查**；B 站被限流时自动退回博查，不会空手。
> **前端仍未接播放** —— 见下方「已实现 / 未实现」。

**改之前是什么样**

检索底层是 `backend/src/service/video/service.py` 的 `ExternalVideoService.search()`，
它直接打 `api.bilibili.com/x/web-interface/search/type`，只带了 `User-Agent` 和 `Referer`，
有三个雷：

1. **没有 wbi 签名、没有 `buvid3` cookie**。B 站 2023 年起给 web 接口加了 `w_rid` + `wts` 校验（要先请求 `nav` 拿 `img_key`/`sub_key`，按固定重排表混出 `mixin_key` 再 MD5），还会给未登录请求发指纹 cookie。这套裸调用**在开发机可能能用、在云服务器 IP 段大概率被风控挡**（B 站对机房 IP 特别敏感）。
2. **静默失败**：`except Exception: return []`。接口挂掉时前端只看到"没有推荐视频"，**根本排查不出是接口坏了**。
3. **没有任何限流**：它在资源生成链路里，用户每生成一次资源就打一次 B 站。

**已实现**（已用真实 API 跑通）

- [x] **不在代码里逆向 wbi**：视频走的是**不需要签名**的老接口 `x/web-interface/search/type`，带上 `buvid3` 指纹即可通。新接口 `x/web-interface/wbi/search/type` 会下发 `v_voucher` 验证挑战 —— **解不了也不去解**
- [x] **域名白名单落到 `backend/src/utils/education_sources.py`**，作为唯一事实来源（不是散在业务逻辑里的 `if`）
- [x] **白名单用博查的 `include` 参数在 API 层限定**，并在结果侧再按域名筛一遍兜底（`include` 只是请求侧建议，实测可能仍返回名单外站点）
- [x] **`_extract_bvid()` 只在解出 BV 号时才给 `embed_url`**，非 B 站来源和 b23.tv 短链一律留空
- [x] 失败可见：不再 `except: return []` 无声吞掉，日志会记录未配置 / 超时 / HTTP 状态码
- [x] 上游 `search_and_save()` 与 `_search_external_videos_early()` **一处未改**（返回结构保持不变）
- [x] **熔断**：被 412 / 429 或 `v_voucher` 拦下就静默 10 分钟（`BILIBILI_CIRCUIT_SECONDS`），期间直接走降级，**绝不继续打接口** —— 越打封得越久
- [x] **相关性过滤**：B 站接口**永远返回满页**，"返回了 N 条"是假信号。用本地 BGE 模型按余弦相似度筛一遍（`EXTERNAL_VIDEO_MIN_SIMILARITY`，默认 0.55），见下方「实测数据」
- [x] **双源 + 降级**：B 站取视频，课程平台 / 图文**始终**由博查补（这是博查的长处，B 站覆盖不到）；只有 B 站**真的没拿到**时才动博查的 B 站档兜底 —— 平时比原方案**省一次付费调用**
- [x] **节点级接口**：`GET /path/{path_id}/node/{node_id}/external-videos`，检索词取自节点的 `knowledge_tags` 而**不是节点标题**
- [x] **明确不做**：轮换 `buvid3` 指纹去绕限流 —— 那是规避风控，性质不对

**实测踩到的两个坑（都已在代码里处理，别再踩回去）**

1. **B 站必须单独查一次。** 通用的网页搜索在 B 站返回的绝大多数是**图文专栏（`/read/`）、付费课程（`/cheese/`）、收藏夹（`/medialist/`）和旧格式 AV 号**——实测限定 `bilibili.com` 抓 20 条，真正的 `/video/BV` 页只有 2～6 条。所以把 B 站和十几个课程站点放在一次查询里时，B 站的名额会被挤光，**一条视频页都剩不下**。现在拆成两次查询（`include_domains("embed")` 与 `include_domains("course", "reading")`），B 站优先占位。（**2026-09-28 更新**：视频改由 B 站接口直接提供后，这两次博查查询里 `embed` 那档已降级为「B 站没拿到时」的兜底，`course` 档照旧常查。）
2. **只保留能播的单个视频页。** `embed` 档上只有 `/video/BVxxx` 算视频，其余一律丢弃；有 BV 号时把地址归一成 `https://www.bilibili.com/video/{bvid}`，顺带去掉 `m.` 移动域名和 `?from=search` 之类的尾巴，同一集的多个地址会因此被去重。

**实测数据（真实 API 跑的，不是推测）**

博查在 B 站视频上是**结构性召回失败**，换查询词救不回来：

| 查询 | 博查返回真视频 | B 站接口返回真视频 |
|---|---|---|
| `RAG 检索增强生成` | 0 / 20 | 20 / 20 |
| `上下文窗口 大模型` | 2 / 20 | 20 / 20 |
| `企业级RAG系统` | 0 / 20 | 20 / 20 |
| `线性代数 教程`（对照组） | 3 / 20 | 20 / 20 |

11 组查询（宽窄都有）用博查总共只捞到 **15 条**真视频页，平均 1.4 条；其余全是 `/read/` 专栏、`/cheese/` 付费课、`/medialist/` 收藏夹、`/opus/` 动态。原因是博查是**网页**搜索引擎：B 站视频页 JS 渲染、正文稀薄，索引质量天然差，永远排在有真实正文的专栏文章后面。**这不是查询词问题，是索引结构的差距。**

但 B 站接口有两个必须知道的坑：

1. **IP 级限流，而且会升级到全封。** 实测约 60 次请求后**全部 412**；换全新 `buvid3` 指纹照样 412、间隔拉到 3 秒、复用连接都一样 —— **封的是 IP 不是指纹**，且没有可预期的恢复时间。开发机因此被封过。生产服务器是另一个 IP、按低频调用大概率能用，但**不能把演示押在"希望它不封"上**，所以降级路径是必须的。也正因如此，**不做指纹轮换**（那是规避风控，性质不对，而且只会加速封禁）。
2. **相关性不稳定，"有结果"是假信号。** 接口**永远返回满页**，哪怕查询毫无意义。实测节点「分组聚合与结果导出」召回「origin合并两个文件」、「Service 层单元测试与数据隔离」召回「Cr2O3多壳层EXAFS拟合」。规律是：**行业通用概念名搜得到，我们自己编的教学式标题搜不到**。所以检索词改用节点的 `knowledge_tags`（`Token计数 上下文窗口`、`BM25原理 RRF融合`）—— 实测 1370 个节点**标签覆盖率 100%**，不会退回到那条差路径。残留风险是「课程导航」「学习目标拆解」这类元节点标签也是自造的，召回会差。

   相关性过滤的阈值是在 **16 组真实配对**上标定的：相关 0.348~0.778、不相关 0.385~0.541 —— **两个分布是重叠的**，不存在能干净分开的阈值。0.55 在这个样本上恰好精度 100%、召回 8/9，但最高不相关(0.541)与最低保留相关(0.548)只差 **0.007**，**这点余量是运气不是信号**，换个语料就会变。所以它是**偏精度**的过滤：宁可漏掉几条好的，也不要在学习页上推 EXAFS 拟合。嫌严就把 `EXTERNAL_VIDEO_MIN_SIMILARITY` 调低（0 = 不过滤）。

**还没做**

- [ ] **前端内嵌播放**：全仓 grep 确认前端**从不读** `embed_url` / `cover_url` / `preview_url`，资源库视频卡片只渲染标题 / 来源 / 日期，「打开」弹的是**纯文字摘要** —— 内嵌播放**从来没接上**
- [ ] 独立的搜索入口 + 结果列表页（搜索框、结果卡片、播放/跳转）
- [x] ~~博查不返回视频封面、时长、播放量~~ → **已由 B 站接口补上**（`play` / `duration` / `pic` / `author`）。接口返回已带 `duration_text`、`view_count_text`、`cover_url`、`author`，前端直接可用
- [ ] 检索结果纳入资源库的更细分类（现在只按 `external_video` 归到「视频」）
- [ ] **资源生成链路的检索词还是主题本身**（`search_and_save(topic)` → `_node_query` 退回「去标点的标题」）。这条链路只有用户输入的资源主题、拿不到节点的 `knowledge_tags`，所以召回不如节点级接口。好在主题是用户自己输入的，比我们编的课程标题更像搜索词，风险较小；要更好就得在 `resource/service.py:589` 那侧多传一个标签参数

**合规来源白名单**（实现在 `backend/src/utils/education_sources.py`）

关键设计：**一个搜索 API + 一张域名白名单**，而不是 N 个爬虫。各家教育平台**都没有开放搜索 API**，自己爬等于把上面三个雷复制 N 份；搜索 API 一次调用拿回结果，按域名过滤即可，成本为零。

> **2026-09-28 更新**：白名单现在只管**博查那条链路**（课程平台 + 图文）。B 站视频已改由 B 站接口直接给，结果天然都在 B 站，不需要白名单过滤；`bilibili.com` / `b23.tv` 仍留在白名单里，是给博查兜底档用的。

| 档 | 站点 | 域名 | 渲染方式 |
|---|---|---|---|
| A | B 站 | `bilibili.com`、`b23.tv` | **内嵌**：`player.bilibili.com/player.html?bvid=` 官方外链播放器（b23.tv 短链解不出 BV 号，退化成跳转） |
| B | 国家智慧教育平台（**教育部官方**，聚合中小学 / 高等教育 / 职业教育） | `smartedu.cn`（覆盖 `higher.` / `basic.` 子域）、`nvic.com.cn` | 跳转 |
| B | 中国大学 MOOC（网易 + 高教社） | `icourse163.org` | 跳转 |

| B | 网易公开课 | `open.163.com` | 跳转 |
| B | 慕课网 | `imooc.com` | 跳转 |
| C | 图文参考 | `developer.mozilla.org`、`runoob.com`、`juejin.cn`、`github.com`、`arxiv.org` | 跳转 |

- 共 13 个域名，远低于博查 `include` 的上限（文档称 100，一说 20）
- **只有 A 档能嵌播放**。B 站外链播放器对**版权受限内容会拒绝播放**，接前端时要准备"该视频不支持站外播放，点此跳转"的兜底
- iframe 要加 `referrerpolicy="no-referrer"`，否则部分浏览器会拦
- **腾讯课堂已于 2024-10-01 正式停止运营，不要写进白名单**

- 不下载 / 不转存任何视频文件，**只存元数据 + 外链**
- 不逆向签名、不绕过任何平台的风控或权限校验

### 4. 出题难度动态调整

> **状态：大半已实现。别讲成"我们要新做动态难度"** —— 会被追问穿。

**已有的（核实过）**

- 难度**确实在往下传**：`exam_router.py:14-19` → `generate_and_save(difficulty="medium")`（`exam/service.py:350-357`）→ `resource_graph.py:1833` → 提示词变量 `{difficulty}`（`resource/exam.yaml:8`）。
- **节点测验已有自适应**：`path/service.py:1360-1379`（流式版 `:1461-1479`）依 `previous_state.score` 调 `adjust_quiz_difficulty`。规则在 `path/difficulty.py:33-56` —— **低于 60 降一级、高于 85 升一级，每次最多升/降一级**。
- 难度配比也已闭环：画像的 `memory/understanding/application` 三档 → `easy/medium/hard` 百分比（`portrait/service.py:1340-1348`）→ `build_learning_guidance` → 注入出题提示词。

**真正的缺口（三个）**

- [ ] **全局考试不走自适应** —— 只有节点测验有 `adjust_quiz_difficulty`
- [ ] **所有聚合都用全量记录、没有"最近 N 次"窗口**：雷达（`portrait/service.py:1118`）、统计（`exam/service.py:794`）、会话列表（`:751-756`）全是全量。后果是**半年前的错题永远压着当前分数** —— 这才是"难度调不准"的根因。改动收益最大的一处是雷达的 `memory/understanding/application`，因为它直接喂给出题配比
- [ ] `ResourceService` 直接存题处**写死 `"medium"`**（`resource/service.py:213`）
- [ ] **难度调整要能解释**：规则（`difficulty.py`）和配比文案（`learning_guidance`）都已经存在，前端串起来展示即可，几乎不用新造

**正确的讲法**：「难度有两级自适应 —— 节点测验按上一题得分升降档，出题配比由画像三档驱动」。

## 二、界面

### 5. 能力雷达图优化

**现状**

- 雷达图是**六维**：记忆、理解、应用、分析、广度、坚持。前后端一致（`portrait_radar_model.py` 六个字段、`portrait/service.py` 的 `_format()`、前端 `ProfilePage.vue` 的 `fallbackDimensions`），设计文档也写死了六维。
- **只能看"当前"**：`portrait_radar` 每用户只有**一行**（`user_id` 是 unique），每次重算直接覆盖，历史留不下来。
- **维度点不开**：只能看到分和一句描述，看不到分数是怎么构成的。

**要做**

- [ ] 维度可展开：点开看这个分由哪些题、哪些知识点贡献
- [ ] 历史轨迹：需要先解决持久化 —— 要么加一张快照表（每次重算写一条），要么按学习事件的时间窗现场重算两次
- [ ] 视觉升级：分层填充、动效、hover 高亮、空数据态，与首页色板统一

**六个维度分别是怎么算出来的**（`portrait/service.py:1106-1192`，核实过）

| 维度 | 真实算法 |
|---|---|
| 记忆 | `ExamQuestion.difficulty == "easy"` 的正确率 |

## 四、检索架构（RAG）

**现状链路**：文件 → 提取文本 → 按 **1000 字**切块（150 字重叠）→ 每块算一个向量 → 向量以 **JSON 文本**存进 MySQL 的 `knowledge_vectors.embedding` → 检索时把**全表**拉进 Python 算余弦、排序取 top_k → 拼成一段纯文本返回。

先说实话：**现在语料只有几百段（公共 342 + 私有 176），全表扫描还跑得动**。所以下面这批改造，一半是为了**上量不崩**，一半是因为这套架构在答辩时站不住。其中 RAG-1 是**真 bug**，RAG-2 是**效果提升最直接**的一条。

### RAG-A 切割方法（含一个真 bug）

**现在的做法**（`backend/src/utils/file_processor.py:66`）：

```python
chunk_text(text, max_chars=1000, overlap_chars=150)
# 保留标题路径 → 按段落聚合 → 超长段落再按句子切 → 相邻块补 150 字 overlap
# 唯一调用点：knowledge_router.py:142
```

> **纠正**：上面注释里的「相邻块补 150 字 overlap」**不准确**。`_add_overlap`（`file_processor.py:179-190`）做的是**前缀注入** —— 把上一块尾部的 150 字以 `上文摘要：...` 的形式拼到当前块的**开头**，不是字符级重叠。语义不同，改法也不同。

方法本身不算差（有标题路径、有上下文衔接、不是粗暴按字长截断）。问题出在**参数和下游不匹配**：

- **bug**：切块是 **1000 字**，而入库用的 `BAAI/bge-small-zh-v1.5` **默认最大 512 token**（约 500～700 汉字），模型自带的 `config.json` 里 `max_position_embeddings: 512`，而全仓库**没有任何 `max_seq_length` 的设置**（grep 0 命中）。结果：**每块的向量只反映前半段**，后半段在检索时等于不存在 —— 能不能被检索到，取决于内容是不是恰好在块的开头。
- **长文档尾部会产生被静默丢弃的碎片**：`<50` 字的 chunk 会被 `ingest` 直接拒绝（`knowledge_base.py:193-194`），调用方只把它计入 `skipped`（`knowledge_router.py:145`），既不报错也不提示。
- **块内结构会被切碎**：按句子切分不认识代码块和表格，代码/表格可能被腰斩。
- **块与返回长度互相打架**：块 1000 字，但检索返回时又按 `RAG_RESULT_MAX_CHARS=1200` 截断，凑不齐完整小节。

**升级方向**

- [ ] 块长按**模型窗口**定，别拍脑袋：`max_chars ≈ 窗口 × 0.8`（bge-small 512 token → 约 400 字；换 `bge-m3` 后可以放到 1000+）
- [ ] 改成**按标题层级切**（Markdown 的 `#/##/###`、PDF 的章节），块内保留完整小节，而不是纯粹按字数
- [ ] **父子块（small-to-big）**：用小块（约 300 字）做检索、命中后把它所属的**整个小节**喂给模型 —— 兼顾检索精度和上下文完整，对"按小节生成讲义"这种场景特别值
- [ ] 代码块、表格**不切**
- [ ] 改完**必须重建全部向量**（否则新旧混存，见 RAG-H）

### RAG-B 换掉现在的 embedding 模型（最该换的一环）

**现状**：用的是 `BAAI/bge-small-zh-v1.5` —— BGE 系列里**最小的一档**（约 24M 参数、512 维、**512 token 窗口**），而且是 2023 年的版本。企业里做中文 RAG 现在普遍用 `bge-m3` 或 `bge-large-zh` 这个量级，差得确实不是一点。

| 模型 | 维度 | 窗口 | 特点 |
|---|---|---|---|
| `bge-small-zh-v1.5`（**现在用的**） | 512 | 512 token | 小、快，但中文语义和长文本都弱 |
| `bge-large-zh-v1.5` | 1024 | 512 token | 中文效果明显更好，窗口没变 |
| **`bge-m3`（建议）** | 1024 | **8192 token** | **多语言 + 长窗口 + 同时输出 dense / sparse / 多向量**，目前中文 RAG 的主流选择 |
| `bge-reranker-v2-m3` | — | — | reranker 侧配套（见 RAG-F） |

**为什么建议 `bge-m3`** —— 一次解决三件事：

1. **长窗口 8192**：RAG-A 的切块 bug 直接消失（1000 字的块不再是问题，甚至可以直接按小节切）
2. **自带 sparse 输出**：正好当 RAG-E 混合检索的**关键词一路**，不用再单独接 BM25 —— 一举两得
3. **多语言**：以后要接英文资料、或者企业语料是中英混排的，不用再换一次

**代价（必须说清楚）**

- [ ] **换模型 = 全量重建向量**。维度从 512 变 1024，旧向量**全部作废**，必须重新嵌入一遍（`knowledge_vectors` 全表）。这正好会踩到 RAG-H 的"静默丢向量"，所以**先修 RAG-H 再换模型**
- [ ] **服务器没有 GPU**。`bge-m3` 在 CPU 上比 `bge-small` 慢不少：批量入库可以离线慢慢做，但**单次检索的编码延迟**要实测；如果不可接受，退一档用 `bge-large-zh-v1.5` + MySQL 全文索引提供关键词一路
- [ ] **国内拉模型的问题**：现在 `_get_embed_model_async()` 本地目录没有就去 HuggingFace 直连下载，而 `main.py` 启动时会 `await` 它且**没有 try/except** —— 拉不到模型 = 后端起不来。换模型要么走 HF 镜像，要么**把模型文件预置到 `backend/src/ai_core/knowledge_base/` 下**再启动
- [ ] 模型文件体积：`bge-m3` 约 2 GB 级，注意服务器磁盘和镜像大小

### RAG-C 向量库怎么选

**现状**：向量以 **JSON 文本**存在 MySQL 的 `knowledge_vectors.embedding`，检索时把全表拉进 Python，`json.loads` 逐条反序列化再算点积 —— **没有任何 ANN 索引**，而且 JSON 比二进制大 3～4 倍。

| 候选 | 形态 | 适合我们的理由 / 代价 |
|---|---|---|
| **FAISS**（建议先上） | 进程内库 | 纯 CPU、**不用新增服务、不用改数据流**；几百～几万段完全够。代价：索引在多进程下要各自加载 |
| Qdrant | 独立服务 | 运维友好、原生支持元数据过滤；要新增一个容器 |
| Milvus | 独立服务 | 功能全但重，得等语料上到十万级才值 |
| Redis Stack | 复用现有 Redis | 已经有 Redis，换 `redis-stack` 镜像即可走 RediSearch 向量索引；代价：镜像换了、内存占用上去 |
| pgvector | 换数据库 | 要从 MySQL 迁到 PostgreSQL，代价最大 |

- [ ] 建议：**先 FAISS**（不新增服务、不改数据流），向量存二进制，`doc_id` 与 MySQL 一一对应
- [ ] 职责分开：MySQL 存正文与元数据，向量侧只存 `doc_id` + 向量
- [ ] 语料上量后再评估要不要换成 Qdrant

### RAG-D 调用方式

**现状**：一个函数 `search(query, top_k, user_id, category)`，**返回拼好的纯文本字符串**，被 6 个地方直接 `await`：

| 调用点 | 传什么 | 影响 |
|---|---|---|
| `ai_core/resource_graph.py:827, 1490` | `f"{topic} {section_title}"`, top_k=3 | **在 section 循环里 —— 每生成一节就查一次**，一篇 6 节的讲义 = 6 次全表扫描 |
| `ai_core/tools/knowledge.py:257` | 模型自己给的 query | 作为智能体工具被 LLM 调用 |
| `service/path/service.py:240, 574` | `subject`, top_k=5 | 生成学习路径时按科目查 |
| `service/resource/generation_context.py:131` | `topic`, top_k=3 | 资源生成上下文，与主流程并发 |
| `service/mock_classroom/service.py:271` | query, top_k=5 | 模拟课堂评分时取依据 |

问题：

- **返回字符串** → 调用方拿不到结构化结果，**没法做引用、重排、去重**，只能整段塞进提示词
- **讲义生成是"每节查一次"**，是全表扫描的性能放大器（代码里那个 `RAG_GLOBAL_SEARCH_CONCURRENCY=20` 的全局信号量，其实就是在给这件事踩刹车）
- **参数散落**：top_k 有的 3 有的 5、`category` 几乎没人传、重复主题每次都重算

**升级方向**

- [ ] 统一成 `retrieve(query, *, top_k, user_id, categories, mode)`，返回**结构化 `list[dict]`**（doc_id / 标题路径 / 分数 / 正文），文本拼接交给调用方
- [ ] 加批量入口 `retrieve_many(queries)`：讲义生成**一次扫描覆盖整篇多节**，而不是循环里查 N 次
- [ ] 检索结果加缓存（query + 用户可见范围做 key），同一主题重复生成时直接命中
- [ ] 把 `RAG_*` 参数收进统一的配置模块，别再散在 `os.getenv`

### RAG-E 混合检索：向量 + 关键词

- **现状**：纯语义向量一路到底。对**专有名词、API 名、版本号、编号**召回很差（`code2session`、`langgraph`、`v1.0.5` 这类），而"智能体开发"这套语料**满篇都是**。
- [ ] 加关键词一路：MySQL 全文索引（`ngram` 解析器支持中文）或 jieba + BM25

### RAG-F 加 rerank

- **现状**：没有。一次向量召回直接定生死，排在第 7 位的正确文档永远进不了上下文。
- [ ] 召回放大到 top-20 → `bge-reranker-base` 重排 → 取 top-5（CPU 可跑）

### RAG-G 查询侧与结果侧

**后果**：系统对外暴露了一个「联网搜索」能力，实际调用返回空。

**选型结论**

- **不要选 Bing** —— Bing Search API **已于 2025-08-11 退役**（LangChain 的 `BingSearchAPIWrapper` 跟着一起死了）
- **选博查（Bocha）**：国内服务、延迟低、**数据不出境**（教育产品这点重要），中文质量好，是 DeepSeek 官方联网搜索的供应商；除 Web Search 外还有 **Semantic Reranker API**，**顺带能补 RAG-F 那一环**
- 备选智谱 Web-Search-Pro（更便宜，OpenAI 兼容 + 允许流式）
- **不选抓取类**（Apify / Bright Data / SerpApi）：痛点正是"抓取不稳"，换个抓取源只是换个地方不稳；而且 Google 已在起诉 SerpApi，有政策风险
- ⚠️ 价格口径各家来源不一致（博查约 ¥36/1000 次、智谱标准版约 ¥10/1000 次），**以官网为准**

## 建议顺序

| 顺序 | 做什么 | 理由 |
|---|---|---|
| **0** | **建 RAG 评测脚本**（跑 `kb-qa-set.json` 的 hit@k） | **最该先做的一件事**。没有基线，后面每一条 RAG 改造都没有证据。⚠️ 评测集只在提交物目录，脚本要走可配置路径，别硬编 |

| 2 | 第 7 条（学前后对比） | 复用上一步的快照表；**顺便把硬编码的 `- 60` 基准拿掉**（现在那个 `+18%` 是假对比） |
| 3 | 第 6 条（路径导图页） | 数据现成（`get_current_path` 已返回 status/resources/weak_points），纯前端 + 一个路由，**演示冲击最强** |
| 4 | RAG-A（修 1000 字切块超窗口的真 bug，**先修 RAG-H**） | 真 bug，且是"能不能检索到"的分水岭 |
| 5 | RAG-E（混合检索）+ 给 `knowledge_vectors` 加索引 | 对满篇专有名词的语料提升最直接；索引是纯收益 |
| 6 | 批量检索（消掉"每节查一次"） | PPT 标准档现在是 **11~14 次全表扫描**，语料上量前必须做 |
| 7 | 第 3 条（主智能体可切换） | 最小版本只动前端，后端现成；「面向非智能体用户」的最大卖点 |
| 8 | 第 2 条（交代码） | 卖点强、技术干净（纯静态分析），守住"不执行代码"即可 |

## 附：已核实的口径（别再凭印象说）

- 能力雷达图是**六维**，不是"多维多维"：记忆 / 理解 / 应用 / 分析 / 广度 / 坚持。
- 系统里另外一组多维在**进阶实践**：**4 个评分维度**（问题理解 / 证据与依据 / 方案取舍 / 验证方法，见 `advanced/practice_service.py` 的 `CRITERIA_LABELS`），以及**6 个通用阶段 id**（老会话用的阶段词汇）。这两个和雷达图不是一回事：一个是"这个人的能力画像"，一个是"这一份作业合不合格"。
- 雷达图的六个维度全部由**真实答题记录**算出，**不是用户自评**（这点是对的）。但「坚持」那一维**只用了考试记录**，见下面的纠正。
- RAG 现在用的 embedding 是 **`BAAI/bge-small-zh-v1.5`**（512 维、512 token 窗口、约 24M 参数），**不是** `bge-m3` 那一档 —— 换模型是**计划**，别讲成现状。
- RAG 的切块是 **1000 字**，而模型窗口只有 512 token 且没设 `max_seq_length` —— 这是** bug**，不是设计取舍，别当特性讲。
- RAG 那个 `overlap_chars=150` **不是字符级重叠**，`_add_overlap`（`file_processor.py:179-190`）是把上一块尾部当作 `上文摘要：` **前缀注入到下一块开头**。别描述成"相邻块重叠 150 字"。
- **「坚持」维度只统计考试天数**（数据源是 `ExamRecord`，`portrait/service.py:1152-1162`），不是"阅读和答题行为"。一个连看 30 天资料但没考试的学生，坚持度是 0 —— 说成"六个维度全部由真实答题和阅读行为算出"**是错的**。
- **`learning_events` 这张表只写不读**：5 个写入点、0 个读取点。别把它讲成"系统在用的学习行为数据"。
- **`OverviewPage` 上那个 `+18%` 的对比基准是硬编码的 60**（`OverviewPage.vue:89` 的 `masteryScore - 60`，图表目标线 `target: 60`），**不是"学之前 vs 学之后"**。别把它讲成学情对比。
- **「动态难度」已经实现了大半**：节点测验早就在按上一题得分升降档（`path/difficulty.py:33-56`）。真正的缺口是"全局考试不走自适应"和"聚合用全量而非最近 N 次"。别讲成"我们要新做动态难度"。
- **小程序的前置不是备案**：域名 `zhiban.website` 已经在对外服务（`deploy/nginx/zhiban.website.conf:2-3`），缺的只是 HTTPS 证书，而宝塔的申请钩子已就位。别讲成"卡在备案域名"。
- **联网搜索走博查**（`backend/src/utils/web_search_client.py`），**视频另走 B 站官方搜索接口**（`backend/src/utils/bilibili_client.py`，带 `buvid3` 指纹 + 熔断 + 相关性过滤 + 博查降级）。改之前：联网搜索走自建 SearXNG（**从来没部署过**，`deploy/` 只有 nginx、`.env` 无 `SEARXNG_*`，6 个入口实际一直返回空）；视频检索走 B 站裸接口（**没有 `buvid3` cookie**、失败静默返回空、无任何限流、无相关性过滤）。SearXNG 那套**已彻底删除**，别再把 SearXNG 讲成现状。
  - ⚠️ **别把"视频检索也统一走博查"讲成现状** —— 实测博查在 B 站视频上平均只捞到 1.4 条真视频页（见「一 · 1」）。讲"统一走博查"会被实测打脸。
  - ⚠️ **别把 B 站接口讲成"稳定可用"** —— 它会被 **IP 级 412 全封**（换指纹无效），所以才有熔断和博查降级。正确的讲法是「**双源 + 自动降级**」，而不是「我们换了个更好的源」。
