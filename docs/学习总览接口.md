# 学习概览接口说明

本文档记录学习概览页面使用的后端接口。概览页面只需要调用聚合接口，后端负责读取画像、路径、科目进度、诊断和学习记录，前端不再并行拼接多个接口，也不在读取页面时生成学习路径。

## 1. 鉴权约定

所有接口都需要登录用户的 JWT。

```http
Authorization: Bearer <access_token>
```

为兼容旧客户端，也可以同时携带：

```http
token: <access_token>
```

未登录或 token 失效时返回 HTTP `401`。前端应清理本地登录状态并回到登录页，不要把 token 放到 URL、日志或错误提示中。

## 2. 概览主接口

### `GET /study/overview`

返回当前用户的学习概览快照。请求不需要 query 参数或 request body。

```http
GET /study/overview
```

统一响应包装：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

### 2.1 返回字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `profile` | object | 用户首次学习定向保存的身份、方向和目标；另有 `learning_signals`（画像里与学习行为有关的信号） |
| `path` | object | 当前学习路径、整体节点进度和路径内相对难度序列；**`completed` 见下方 2.3** |
| `paths` | array | **全部**路径的路线图（名称、完成度、当前节点、节点状态序列、上次学习日期），见下方 2.7 |
| `subjects` | array | 用户已加入路径对应的科目完成度和学习时长 |
| `goals` | array | 当前路径节点清单，可用于目标勾选列表 |
| `next_content` | array | 当前处于进行中或已解锁状态的下一步内容 |
| `blind_spots` | array | 按掌握度筛选后的薄弱知识点（带 `node_id` / `node_title` / `path_id`，可跳到那一章的复习）。**2026-10-01 起概览页只用它的第一条**当「当前卡点」，完整列表属于学习画像页 |
| `diagnosis` | object | 当前综合掌握度、阶段和已作答数量 |
| `mastery_bars` | array | 图表用知识点掌握度数据；没有练习记录时使用六维能力 |
| `radar` | object | 记忆、理解、应用、分析、广度、坚持六维能力数据 |
| `study_history` | array | 最近 7 天实际累计学习时长，可用于学习轨迹图 |
| `summary` | object | 学习总时长、活跃天数、节点完成数、掌握度摘要和答题正确率；**`total_study_seconds` / `active_days` 目前恒为 0，见下方 2.4** |
| `activity` | object | 近期活跃度：**本周**每天的活跃格、最后一次学习是哪天、本周答了几题 / 通过几次节点测验 / 读了多久，以及**近几周每周的学习天数**（见下方 2.4.3） |
| `resources` | object | 资料库那一块的计数：共几份、已读几份、未读几份、收藏几份。**纯转手** —— 就是 `get_stats` 为算 `open_rate` 已经算过的那一份（`total` / `read_count` / `unread_count` / `collected_count`，外加 `by_type` 等），一条新查询都没有。页面说「共 36 份，已读 12 份」，**不给百分比、不写成「12 / 36」** |
| `recommendation` | object | 当前系统判断、推荐行动、推荐理由、完成标准，以及推荐指向的节点本身（`target`，见下方 2.5） |

### 2.2 空数据约定

用户尚未完成学习定向、尚未生成路径或没有练习记录时，接口仍返回 `200`，但对应字段为空或为 `null`：

- `subjects`、`goals`、`next_content`、`blind_spots`、`study_history`、`mastery_bars` 返回空数组；
- `path.id` 可以为 `null`，进度为 `0`；
- 没有当前路径时 `path.difficulty_trend` 返回空数组；有路径时首节点的 `difficulty_score` 固定为 `1.0`，`relative_difficulty` 仅用于当前路径内的图表高度；
- `diagnosis.score`、`summary.mastery_score`、`summary.correct_rate` 可以为 `null`（`correct_rate` 在**一题都没答过**时就是 `null`），`diagnosis.stage` 为 `正在生成`，`summary.text` 为空字符串；
- `recommendation.status` 为 `generating`，没有可执行节点时 `target_id`、`action` 和 `target` 为 `null`；
- `activity.active_days_this_week` 为 `0`、`activity.read_seconds_this_week` 为 `0`、`activity.last_active_date` 为 `null`；`week_start_date` **仍然是本周周一那天**（新人也有）。

前端应根据这些字段显示“正在生成”或空状态，不能填充示例科目、进度、时长或推荐结论。

`activity.last_active_date` 的 `null` 有确切含义：**窗口内（默认 30 天）没有任何学习行为**。超出窗口的记录连日期都不参与计算，所以它不会一直挂着三个月前那个陈旧日期。`activity.window_days` 就是那个窗口，页面文案里的“最近 N 天没学习”应当取它，不要在前端另写一个 30。

`active_days_this_week` 数的是**本自然周（周一为第一天）到今天**，不是滚动 7 天。滚动窗口的起点每天都在动，学生没有哪一天是对齐它的 ——「近 7 天来了 4 天」既不是“这周”也不是“上周”，读完不知道能干什么。`week_start_date` 给出本周周一，页面不必自己算（前端算就会各写一份归日规则，在时区上走偏）。

注意归日仍走 `portrait/service.py` 的 `active_day`（**UTC 日**），与雷达的「坚持」维度同源；UTC+8 的凌晨学习会被归到前一天。这是刻意保持的一致，别在这里另写一套本地时区归日。

### 2.4.2 `activity` 里另外三个数：七格、答题数、过关数

`active_days_this_week` 只出一个数，答不出"断在哪一天"。所以另给 `weekly_days`：**固定七格，周一起**，每格 `{date, active, is_today}`。

- **七格一起给，不给"活跃的那几天"** —— 缺掉的那几天正是这一项要说的信息。后半周还没到的日子也在里面，`active` 为 `false`，页面照画。
- `active` 的口径和 `active_days_this_week` 完全一致（同一次归日、同一个并集），只是逐日摊开。带上界 `<= today`，防止时钟偏移把明天点亮。
- `is_today` 由服务端给，页面**不要自己算今天** —— 那是浏览器本地日，和服务端的 UTC 归日差一个时区。

`questions_this_week` / `quizzes_passed_this_week` 回答"本周做了多少"，两个都**零额外查询**：`get_stats` 早就把 `ExamRecord` 全表和近 30 天的 `LearningEvent`（带 `metadata`）读进内存了。

- `questions_this_week` 只数**已判定**的作答（`is_correct` 非空）。简答题还没判分时不算 —— 否则会和正确率的分母对不上。
- `quizzes_passed_this_week` 数的是 `node_quiz` 事件里 `metadata.passed` 为真的次数。**交卷（`assessment`）和诊断不参与**，它们不是"过了一关"。页面文案要写「通过 N 个节点测验」，不能写「测验 N 次」——后者是做了几次。

### 2.4.3 `activity.week_trend`：每周学习天数（页脚那张柱状图）

**从早到晚**六个桶，每桶 `{week_start, active_days}`。`week_start` 是那一周的周一（ISO 日期），`active_days` 是那一周里有几天在学习（0–7）。

- 口径与 `active_days_this_week` 完全一致（同一批时间戳、同一个 `active_day`、同一个 `_week_start`），所以**最后一桶的 `active_days` 必然等于七格里点亮的格数**。两个地方对同一周给不出不同的答案。
- **没来的那几周给 0，不跳过。** 缺桶会让横轴撒谎 —— 相邻两根柱子看起来挨着，中间其实隔了好几周。
- 上界挡住未来日期（时钟偏移），所以一桶最多 7。
- 周数由 `_TREND_WEEKS` 决定（当前 6）。**页面不要写死「最近 6 周」，应按数组长度渲染标题**，否则改常数时标题会开始撒谎。
- `active_days` 全为 0 时（新账号）数组**照样给六桶 0**，不是空数组 —— 页面据此把整张图换成一句说明；给空数组前端分不清"没数据"和"字段没给"。

**为什么数"天数"而不是"答了几题"或"学完几个节点"：**

1. **只有它有可信的时间戳。** 节点完成时间（`user_path_progress.completed_at`）**不能**用来画走势：`reconcile_completed_prerequisites` 修复回退状态时会给缺时间戳的记录写上 `datetime.now()`（`path/helpers.py`），于是几个月前学完的节点被盖成"今天"，图上凭空多出一根高柱。`learning_events`（交卷 / 节点小测 / 资料读完 / 课堂对话）和 `ExamRecord` 是当场写的。
2. **任何形式的学都算。** 只读资料、只在课堂上提问的人，用"答题量"画出来是一片空白 —— 那是在说他没学。
3. **值域固定 0–7**，不会被某一周的突击量把其余几周压平。

**查询窗口**：`LearningEvent` 取最近 `_EVENT_QUERY_DAYS`（当前 49 天，= `_TREND_WEEKS * 7 + 7`），比 `window_days`（30）宽。两个窗口各管各的：一个管"取多少行进来"，一个管"哪些行算数"（`last_active_date` 的 30 天语义不变）。仍然是**一条**查询，`ExamRecord` 全表本来就在内存里，整项零额外查询。

### 2.4 `activity`：为什么它不是 `summary.total_study_seconds`

`summary.total_study_seconds` / `active_days` 由 `StudySession` 累计，而 `StudySession.total_seconds` 的**唯一写入方**是 `StudyService.heartbeat`。前端从来没有调用过 `POST /study/heartbeat`，所以这两个数、以及 `study_history`，**结构性恒为 0**。

也就是说：**它们是 0 不是在说“你没学过”，而是在说“这条统计链路没人接”**。页面拿它渲染出的“学习 0 秒”是错的。

`activity` 换成数 `LearningEvent` 与 `ExamRecord` 的**并集**（口径与六维雷达的「坚持」维度同源，共用 `portrait/service.py` 的 `active_day`）—— 这两张表有真实写入方：交卷、节点测验、资料读完、访谈、课堂对话。只数答题会把“看资料 / 做测验 / 上课但没考试”的人算成没来过，所以是并集而不是替换。

想把“学习时长”变成真的，唯一的办法是在前端接上 `POST /study/heartbeat`；**那会得到一个“页面开着多久”的数，而不是“学了多久”**，是更差的指标。所以这一路刻意不接。

### 2.4.1 `activity.read_seconds_this_week`：唯一真实的时长，但它只是「阅读」

要回答“这周花了多少时间”，系统里**只有一个**带真实时间戳的来源：`resource_read` 事件的
`metadata.duration_seconds`。基础讲解页在文档可见时每 30 秒上报一次**距上次上报的增量**
（`FundamentalsPage.vue` 的 `reportReadDuration`），后端把增量累加进
`ResourceReadStatus.duration_seconds`，并写一条事件。于是：

- **加的是增量，不是快照** —— 这里求和不会重复计数；
- **口径是「读了多久」，不是「学了多久」**。测验、课堂、普通对话**都没有记时**。只做测验、
  不读资料的人这里是 `0`，所以页面必须写「本周读了 X」而不能写「本周学习了 X」—— 否则会和
  同一行的「本周来了 N 天」当场打架；
- **会略小于 `recommendation.target.time_spent_seconds`**：`mark_read` 每次都把增量加进
  `ResourceReadStatus.duration_seconds`，但 `duration_seconds < 10` 时**不写事件**（防轮询刷爆
  画像），本周这个和会漏掉零碎的小段。实测同一账号 2815 秒 vs 当前章节累计 2847 秒 —— 两个数
  都四舍五入到 47 分钟，但它们不是同一个数算了两遍。

**别用 `summary.total_study_seconds` 回答这个问题** —— 它恒为 0，原因见 2.4。

### 2.3 `path.completed`：为什么它是一个独立字段

**把整条路径学完的人，`next_content` 必然是空的** —— 而空数组本身是个不可靠的信号：前端分不清它是「还在生成」还是「你已经学完了」。

以前前端只有「正在生成下一步学习内容…」这一个分支，于是**学完的用户会一直看着它转**。所以后端额外给出 `completed`：

```json
"completed": bool(total_nodes) and completed_nodes >= total_nodes
```

前端用它区分那两种情况。**不要用 `next_content.length === 0` 反推** —— 那正是这个字段要解决的问题。

### 2.5 `recommendation.target`：主行动卡的元信息

`recommendation` 原来只给"学哪个节点"（`action` / `target_id`）。学生看得见"学什么"，
看不见"点下去要花什么代价"。`target` 补的就是这一块，**纯增量** —— `action` / `reason` /
`criteria` / `target_id` / `action_type` 一个都没动，老的消费方按原样读不受影响。

**这里是压包，不是新计算**：知识点来自节点的 `knowledge_tags`，资料数和测验进度来自
`get_current_path` 已经算好的 `garden_progress`。没有当前节点时 `target` 是 `null`。

`knowledge_tags` 是**标签名本身**（只保留非空字符串），`knowledge_points` 是它的长度。
两个都给是因为它们的用途不同：卡片上要写「这一章讲：向量检索 / 召回评估 / 重排」，
光有「3 个知识点」这个计数，页面上就只有数字没有内容。**计数与名字同生同灭** ——
`knowledge_tags` 不是数组时两者都是 0 / `[]`，不会出现名字空着、计数还在。

**`target` 里曾经有 `tasks_done` / `tasks_total`，2026-10-01 已删除。** 它们透出的是
`path/service.py` 里的一对**派生计数**：

```python
task_total     = len(node_resources) + (1 if quiz_total else 0)
task_completed = 已读资料数        + (1 if 测验全答完 else 0)
```

也就是说「任务 2 / 5」= 「资料 1 / 4」+「测验 1 / 1」，**只是上面两行的和**，学生做不了、
也找不到这么一件事。概览页照着它渲染出了第三行「任务 n / m 个」，读的人不知道那是什么。
**别再把它加回 `target`。** 下面两行已经完整回答了"这一章由什么组成"。

注意区别：`garden_progress.completed_tasks` / `total_tasks` **本身没删也不能删** ——
`StudyGarden.vue` / `TreeReviewScene.vue` 拿它挑树的生长阶段（`<=0` 给 1、`>=total`
或测验开始了给 3）。是**不该把它当"要做的事"透给用户看**，不是那个字段没用。

`time_spent_seconds` 来自 `ResourceReadStatus.duration_seconds`（基础讲解页在文档可见时
上报真实秒数），**是真的**，和 `summary.total_study_seconds` 那个结构性恒为 0 的不是一回事
（见 2.4）。

**这里没有「预计耗时」**，也不该有：系统里没有任何时长预估的来源（`PathNode` 连时长字段
都没有），编一个数字就是伪造精度 —— 和已经删掉的 `masteryScore - 60` 是同一类错误。
要加就得先在服务端定出一个可解释的口径（按资料字数 / 题目数估），而不是在页面上现编。

**`blind_spots` 的 `node_id` / `node_title` 现在没有前端消费方了**（2026-10-01 概览页重做后
只用第一条当「当前卡点」）。字段保留 —— 那是按标签把薄弱点路由到具体章节的唯一一份数据，
复习入口迟早要用它。

### 2.7 `paths`：所有学习方向的路线图

概览页要展示**全部**路径（不只是当前那条），并画出每条路径的完整路线，所以后端多给一个
`paths` 数组。**纯增量** —— `subjects` 一个字没动。

```json
"paths": [
  {
    "id": 106,
    "name": "大语言模型原理与微调",
    "is_current": true,
    "progress": 85,
    "completed_nodes": 11,
    "total_nodes": 13,
    "current_node": { "id": 139, "title": "智能体开发框架与MCP协议入门", "status": "in_progress" },
    "nodes": [
      { "id": 129, "title": "大语言模型核心原理与核心术语", "status": "completed" },
      { "id": 139, "title": "智能体开发框架与MCP协议入门", "status": "in_progress" },
      { "id": 141, "title": "线上灰度", "status": "locked" }
    ]
  }
]
```

排序是**当前那条永远第一，其余按完成度降序**。页面上从上往下读就是「先看这条、再看那条」。

`nodes` 是**整条路径的节点，按顺序**，用来把路径画成可点的站点。每项要 `id` 而不只是
`status`：页面上点某一站要跳到那个节点的学习界面（`/learning/fundamentals?node=<id>&pathId=<id>`），
只有状态字符串的话这个交互做不出来。`title` 是给鼠标悬停提示用的。

`status` 取值 `completed` / `in_progress` / `unlocked` / `locked`；**字段缺失时按 `locked` 给** ——
不能因为后端没给状态，页面上就出现一个能点但进不去的站点。

`current_node` 是这条路径上第一个 `in_progress` / `unlocked` 的节点，整条学完时是 `null`。

`last_active_date` 是"这条路径最近一次动过是哪天"，**日期字符串或 `null`**（`null` = 这条路径没留下任何时间戳）。

- **取的是 `user_path_progress` 的 `started_at` / `completed_at` 的最大值，不是 `learning_events.path_id`。** 后者是稀疏的：`mark_read` 记 `resource_read` 时压根不传 `path_id`，`assessment` 也显式传 `None` —— 只看事件的话，"这条路径我一直在读资料、只是还没做测验"会被显示成从没学过，正好把「哪条路径在养老」答反。
- 归日走同一个 `active_day`，和 `activity` 那一组同源；给日期不给时间戳，理由同 `last_active_date`。
- **`null` 不等于"还没开始"。** 它只说明没有时间戳，而 `regenerate_path` 承接已完成主题用的是批量 `.update(node_status="completed")`，**不写 `completed_at`** —— 那条路径会有十几个已完成节点却一个时间戳都没有（实测 `机器学习与深度学习基础` 就是 10 / 23）。页面必须分两种说法：有完成节点 → 「暂无记录」，一个节点都没动过 → 「还没开始」。一律说"还没开始"会和同一行左侧的 43% 当场打架。

取数上`_build_path_summaries` **不自己查库**：`last_active` 由 `get_overview` 一次取齐传进去（`_path_last_active_map`，一条按 `user_id` 的查询，不是每条路径查一遍）。这样这个函数在单元测试里仍然能脱离数据库跑。

取数上，当前路径**复用** `get_current_path` 已经拿到的那份，不再查第二遍 ——
`get_current_path` 里带一次状态修复（会写库），一个只读聚合接口不该为同一条路径跑两遍。

### 2.6 `summary.correct_rate`：这一步才拿得到的"正确率"

`exam_summary.correct_rate`（答对 / 已答，0–1）以前没有透出，页面上想显示正确率只能拿
`diagnosis.score` 顶 —— 但那是**各知识点正确率的平均**，和"总正确率"不是一回事（一个答过
20 题的知识点和一个答过 2 题的权重相同）。

一题都没答过时返回 `null`，**不是 0**：服务端算的是 `correct / max(completed, 1)`，直接透出
`0.0` 会被页面渲染成「正确率 0%」，等于把"还没测过"说成"全错"。

`summary.total_study_seconds` / `active_days` 恒为 0 这一条不受影响（见 2.4）。

## 3. 聚合接口读取的现有数据接口

以下接口仍然保留，供其他页面或后端服务使用。学习概览页面不需要直接调用它们；`GET /study/overview` 已在服务端完成聚合。

| 接口 | 用途 | 主要数据 |
| --- | --- | --- |
| `GET /ai_portrait/read_portrait` | 读取用户画像 | 身份、学习方向、学习目标、画像 traits |
| `GET /ai_portrait/radar` | 读取或计算能力雷达 | 记忆、理解、应用、分析、广度、坚持 |
| `GET /learning_path/current` | 读取当前活跃路径 | 节点、节点状态、当前节点、路径诊断 |
| `GET /study/path-stats` | 分路径统计 | 科目完成度、学习时长、路径薄弱点 |
| `GET /study/stats` | 全局学习统计 | 总学习时长、答题统计、薄弱知识点、资源统计 |

其中 `GET /study/overview` 只读这些现有数据，不会调用路径生成接口，不会新增路径或节点，也不会修改用户学习状态。
